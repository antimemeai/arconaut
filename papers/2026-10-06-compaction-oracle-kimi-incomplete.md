## Independent campaign-oracle review — managed compaction (B1)

Scope inspected: `docs/MANAGED_COMPACTION_SUBPLAN.md`, `papers/2026-10-06-compaction-source-consequences.md`, `tests/compaction_campaign_test.cpp` (full), `tests/context_test.cpp:90–246`, `tests/coding_test.cpp:10–29,400–453`, `src/context.cpp` (full), `src/coding.cpp:238–345,630–915`.

### Verdict on the central question

The `Model` in `tests/compaction_campaign_test.cpp:63–123` is a genuinely independent oracle, not a tautology: expected *contents*, *selection sets*, *restore insertion positions*, and *ancestry* are computed from the model's own capture list, and `Model::check` (lines 100–122) asserts exact item bytes, entry identities/order, ancestry, and immutable-original membership after every one of the 160 steps and after each of the 16 physical reopens. Wrong selection/archive/restore logic or mutated original bytes in `src/context.cpp:422–538` would be caught. Only synthetic *IDs* are bound to actual revisions (`context->head() + ".0"`, lines 179, 230), which is the acknowledged and reasonable binding; a wrong ID scheme would still fail the check.

However, there are real oracle holes — three of them consequential — plus several smaller ones.

---

### Finding 1 (consequential): scale-phase mock never asserts what reaches the provider request
`tests/compaction_campaign_test.cpp:463–475` (`MockProvider::respond`, lines 34–45). After the 64-turn summary, the engine assembles a real request, but the mock only counts calls and records `bytes`. Nothing asserts that the serialized request input **excludes** the 8192-byte outputs/`needle-*` content and **includes** only mission + summary (+ the new tool exchange). `mock.bytes` is printed, never checked. A regression in which the settled compacted view is not what `CodingEngine` sends (e.g. request assembled from stale `entries_`) passes silently while "byte reduction" numbers still look right.
- **Fix/oracle:** in the mock, on the post-settlement call, assert the request `input` array equals `context.items()`, contains no `"needle-"` substring, and that `mock.bytes` is within a declared bound of `scale_after`. Same gap exists in the `ManagedToolProvider` case (`tests/coding_test.cpp:435–453`): call-2's request is ignored; assert `provider_discard` is absent and the `managed-real` call+result are present in the actual request input.

### Finding 2 (consequential): paged roundtrip oracle is partially self-referential
`tests/compaction_campaign_test.cpp:285–309`. `exact_entry` is built **from the actual inspected entry** (`auto exact_entry = entry;`), with only `ancestry` taken from the model; then `recovered == expected_bytes` and the parsed `id`/`item` are compared back against `entry` (actual) again. So the paging oracle verifies the hex/offset machinery of `inspect` (`src/context.cpp:540–591`) against itself — corrupted original *bytes* would roundtrip "correctly". Immutable-byte integrity is covered elsewhere by `Model::check`, but **without paging**, so a paging-specific corruption tied to content (e.g. a length miscount on multi-byte UTF-8 that rewrites bytes) is only half-covered.
- **Fix/oracle:** build `expected_bytes` from `expected.originals[original_index]` (+ model ancestry), not from `entry`. Also assert `total_bytes` and `next` fields per page and the `offset == total_bytes` edge (currently clamped silently at line 573 and never exercised); add a negative/non-numeric offset string rejection case (`from_chars` rejects it at line 317 — untested).

### Finding 3 (consequential design consequence, under-oracled): one malformed entry permanently bricks all managed repair, including restore
`src/context.cpp:508` rejects publication whenever `protocol_complete(next)` fails, and `protocol_complete` returns false for any entry whose `type` is non-string (line 264). The red case (`tests/compaction_campaign_test.cpp:152–160`) confirms rejection, but the consequence is that after a single malformed item enters the view, **restore cannot fix it either** (restore publishes through the same gate and does not remove the malformed entry) — the only recovery is the un-managed generic `edit` (used at line 160). That is the CLM-agency escape hatch, so it is defensible, but: (a) it is never asserted that generic edit is the *only* documented recovery and that `engine.turn`'s `validate_protocol` (`src/coding.cpp:638`) also fails in this state (a stuck session is unrecoverable via Lua workflow until an operator/generic edit intervenes); (b) the duplicate-call-ID fixture (line 373–375) leaves the same permanent-brick state and likewise relies on a full-view reset edit. Add an explicit oracle documenting the recovery path, or let `restore`/`archive` remove malformed entries by ID.

### Finding 4: developer-role summary pinning is specified but never tested
`src/context.cpp:384–392` pins any entry with `role` user/system/developer; per plan lines 159–161 a developer-role summary "becomes pinned instruction by explicit choice". No test selects/archives a developer summary and asserts `mandatory-entry` rejection, so the permanence (a model-authored developer summary can *never* be compacted away — cumulative growth) is unverified in both directions (that it pins, and that this is surfaced to the proposer rather than discovered later).

### Finding 5: restore-after-persistent-reorder is only covered by one small case
The campaign model never retains a generic reorder (action 8's same-view edit changes nothing), so `Model::restore` (lines 91–99) only ever models pure capture-order merge. But `publish_managed`'s restore anchors insertions on *live successor positions* (`src/context.cpp:494–505`), which under a persisted reorder can land a restored entry in non-capture position relative to reordered survivors. The parallel-group repair case (lines 354–372) covers reorder+restore for exactly one group at the tail. Either add a campaign action that persists a generic reorder and tracks it in the model, or document the exclusion; the source-consequences paper (gptme byte-range aliasing concern, lines 38–43) explicitly motivates repeated restore/reopen order checks.

### Finding 6: no receipts/replay-side audit assertions (stated honestly as a limitation)
Rejections are audited (`src/context.cpp:322–340`) with the candidate retained, but no test replays and asserts rejected packets, staged-cancel packets, or the `stage` field after reopen; `kind:"history"` inspection is never exercised at all. The plan's "no generic proof/receipt subsystem" scope makes this acceptable, but the campaign paper should state that rejection-audit retention is asserted only via `accepted:false` return values in-process.

### Smaller observations
- `tests/compaction_campaign_test.cpp:159` uses positional `object()[1]` on `view()` — breaks silently if field order changes; use `find("entries")`.
- Scale originals check (lines 458–462) is presence-only (`std::any_of` on items): extra/duplicated originals or a corrupted ancestry on the summary entry at scale would pass; `Model`-style exactness stops before the scale phase. Also no restore/paged-roundtrip of an 8192-byte original at scale, and single-sample latencies with no sanity bound (fine as measurement, but say so).
- `whole_groups` treats interleaved parallel calls as one interval (`src/context.cpp:277–306`) — correct for the protocol as tested; nested/overlapping output-before-call cases are covered by `pending.erase != 1`.
- The 160-step mix genuinely covers stale-after-append/reopen/summary, cancel, stage+generic-edit invalidation, and sparse restore including summary entries and their sources; transitions=160 counts settle-neutral steps too, which is fine since `check` runs after each.
- B1/B2 boundary is intact: no thresholds/token guessing anywhere; generic `edit`/`append`/Lua agency unrestricted (`tests/context_test.cpp:163` asserts it), and `context_manage` omitted-base binding (`src/coding.cpp:783–790`) keeps supplied bases strict CAS — consistent with the gptme stale-summary lesson. Orphan stages never execute on reopen (`tests/context_test.cpp:245`) — verified.
- Crash-gap evidence is limited to process-level reopen; the `Custody` verifier only ever sees empty attempts — no custody-conflict recovery is exercised, matching the plan's "no power-loss claims" caveat.

### Bottom line
The deterministic model is a real oracle for selection/summary/archive/restore/reopen/immutable bytes within the small fixture. The three fixes that matter most: (1) assert the post-settlement provider request content in both scale and `ManagedToolProvider` oracles — currently the "bytes actually shrink at the request boundary" claim is unverified; (2) de-tautologize the paged roundtrip by sourcing expectations from the model; (3) decide and oracle the malformed-entry bricks-managed-repair recovery path. The live semantic/RRC campaign and this review's remaining items (history receipts, developer-summary pinning, persistent reorder+restore) correctly remain open per the plan.
