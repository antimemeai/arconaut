# Independent review: U1 root-journal semantic owner

Scope inspected: `docs/U1_RETAINED_STATE_SUBPLAN.md`, U1-relevant clauses of `docs/CORE_DESIGN.md`, `include/arconaut/retained_state.hpp`, `src/retained_state.cpp`, `include/arconaut/retained_events.hpp`, `src/retained_events.cpp`, `include/arconaut/journal_writer.hpp`, `src/journal_writer.cpp` (scan/append/reject/confirm/resume paths), `tests/retained_state_test.cpp`, `tests/retained_state_crash_test.cpp`, `tests/retained_events_test.cpp`, and `foundation.hpp` (ErrorCode ordering, EffectIntent). Read-only; nothing executed or modified.

## Blockers (confirmed bugs)

### B1. Pre-I/O `bad_alloc` from `FramedJournal::append` leaves a stale `prepared_` on a healthy live journal — phantom uncertain facts, silently permanent dedup of an event that was never written

- **Location:** `src/retained_state.cpp:490` (`prepared_ = std::move(candidate);`), the failure handling at `src/retained_state.cpp:492-496`, and the `catch (const std::bad_alloc &)` at `src/retained_state.cpp:506-508`. Enabling condition in `src/journal_writer.cpp:237-265`: all encoding allocations (`encoded.reserve`, `prepared.reserve`, `encode_journal_frame`, `insert`) occur *before* `AppendAttempt` is constructed (line 276) and before any `write_at`, and append's own catch at 297-299 returns `allocation` without poisoning.
- **Trigger:** a heap-failure cut landing inside `journal_->append(drafts)` during its encoding stage (after `prepared_` is assigned, before the first write). The exception propagates to `append_impl`'s outer catch, which returns `{allocation}` **without resetting `prepared_`** — the conditional reset at 493-495 is only on the non-throwing `!written` path.
- **Consequence:** journal state stays `live`, zero bytes written, `committed_` unchanged, but `visible()` now includes the uncertain candidate facts. From then on:
  - `submit()` of the same event hits the early dedup at `retained_state.cpp:589-592` and returns `{existing=true, evidence=uncertain}` **forever, without ever writing it** — the caller believes an admission is pending on a perfectly healthy writer, and it can never become authoritative via `submit`.
  - `attempt()` exposes an attempt that does not exist on disk.
  - This directly violates the claimed invariant "an allocation error at preparation leaves storage and indexes unchanged" / "actual heap failures preserve prior authoritative state" (sub-plan lines 99-100, 193-194).
- **Recommended fix:** make the reset exception-safe — e.g. in `append_impl`'s `bad_alloc` catch, `if (journal_->state() != JournalWriterState::poisoned) prepared_.reset();` before returning (mirroring the 493-495 condition), or guard `prepared_` with a small RAII resetter disarmed only on the successful swap. Since journal-append allocation is provably pre-I/O (writes/sync don't allocate; post-sync publication uses reserved trivial metadata), an unconditional reset in the catch is also defensible.
- **Oracle gap:** `allocation_before_publication` (`tests/retained_state_test.cpp:428-467`) sweeps cuts 0..127 and its `before_io` branch verifies state/bytes but **never resubmits**, so this defect is invisible. Add: after any allocation failure with `state()==live`, require that resubmitting the identical event succeeds with `evidence==live`, `existing==false`, and synchronized bytes advance exactly one batch.

### B2. `retain_rejection` budgets the proposal against `max_batch_bytes` but not the per-chunk frame headers, envelope frame, and commit — large legitimate rejections fail to retain, returning `capacity` instead of `conflict`

- **Location:** budget computation `src/retained_state.cpp:519-540` (proposal bounded to `max_batch_bytes` via `limit - 4` per add) vs. the nested batch's actual cost charged by `append_impl`'s `add_size` at `src/retained_state.cpp:442-449` (32 bytes per source chunk + 32 + encoded conflict/rejection event + 56-byte commit, all inside the same `max_batch_bytes`).
- **Trigger:** a conflicting/changed-identity submission whose serialized proposal is large — e.g. with limits 1024/4096, a changed admission carrying ~3.9 KB of input. `retain_rejection` accepts the proposal (≤4096), chunks it into 4 source frames, and the nested `append_impl` then rejects with `capacity` because 3900 + 4×32 + 32 + ~20 + 56 > 4096.
- **Consequence:** while recording is healthy, a changed-identity reuse is **not** retained as conflict/rejection — contradicting the claimed "changed identity data is preserved as conflict/rejection, originals remain unchanged" (sub-plan lines 172-175, 205-208). The originals do remain unchanged, but the prescribed retained evidence is silently dropped and the caller receives a misleading `capacity` error.
- **Recommended fix:** compute the chunk count first (`ceil(proposal/max_payload)`) and bound `proposal_size + 32*chunks + 32 + encoded_event_size + 56 ≤ max_batch_bytes` (equivalently shrink the per-add budget), so any proposal accepted for chunking provably fits the nested batch. Alternatively return the original `conflict` error and skip retention explicitly when the proposal cannot fit, rather than masking it as `capacity`.
- **Oracle gap:** no test exercises a conflict/rejection near the batch limit; `duplicates_and_retries` uses a 113-byte proposal only. Add a boundary test at the exact largest retainable proposal size and one byte above it.

## Missing specification oracles (test gaps, no confirmed product defect)

1. **Torn-tail (commit-less) reservation burn is untested.** Sub-plan lines 222-224 and 271-273 require burning counters from "fully decoded CRC-valid pending reservation frames" and testing "complete unsynchronized reservations as consumed." The pending burn path (`src/retained_state.cpp:361-379`) is only reachable for frames in an incomplete trailing batch. `issuer()` (`tests/retained_state_test.cpp:363-384`) covers a *complete* failed-sync batch (staged path). Missing: a journal with a valid committed prefix followed by a reservation frame with no commit; assert `issuer_counter()` reflects the burned counter and the next issued identity is distinct. Also untested: reservations inside a semantically rejected staged batch are burned after `reject_recovery_batch` moves them to `pending_`.
2. **Ledger transition matrix largely untested.** Implemented but without red/green cases: terminal-without-open allowed only for cancellation/unknown (`retained_state.cpp:282-286`) — test both the accepted and rejected dispositions; settling→running regression rejection (287-290); observation-after-terminal rejection (273-275); adapter-receipt-without-open rejection (252-259); duplicate identical terminal observation returning existing state (the `existing()` special case at 161-170). The crash and memory tests never submit an observation except via the reentrancy settle path.
3. **Reentrant/uncertain duplicate-submission of events other than admission** (e.g. decision/invocation while poisoned) is not pinned; only admission is checked (`recovery_and_failed_admission`).
4. **Crash test does not assert resubmission of the original admission post-reconcile returns existing/recovered and leaves the effect file unchanged** — only dispatch no-op is checked (`tests/retained_state_crash_test.cpp:190-192`). The memory test covers the evidence label; the crash profile should pin it against native bytes too.

## Concerns requiring clarification or an experiment (not confirmed bugs)

1. **Duplicate identical *non-terminal* observations double-write.** `key()` returns `nullopt` for observations and `existing()` only dedups terminal ones (`retained_state.cpp:161-170`), so resubmitting an identical running/settling observation appends a second identical fact. The dedup claim is stated over "identity," and observations carry no identity field, so this may be intended — but no doc or test pins it. Clarify the sub-plan or extend the special case.
2. **Same-batch conflict recorded as `RejectedSubmissionEvent` instead of `IdentityConflictEvent`.** The conflict pointer is only set when `existing(committed_, …)` matches (`retained_state.cpp:472-475`); two conflicting same-identity events inside one batch (first one valid, second changed) produce a plain rejection. The proposal bytes are still retained, so nothing is lost, but the envelope kind depends on history placement. Confirm intended.
3. **Retry decision reuse.** `apply` only requires a retry's decision ≠ the invocation's original decision (`retained_state.cpp:234`); one recorded retry decision can authorize multiple successive retries with fresh attempt IDs. "Explicit new decision+retry+attempt" can be read as requiring a fresh decision per retry. Tests use each decision exactly once. Clarify.
4. **In-process reconciliation after receipt-recording failure.** When receipt recording fails by allocation (journal still live), `state()` reports `blocked` via `recording_failed_` (`retained_state.hpp:79-83`), admission closes, and attempts expose `reconciliation_required` — but `reconcile()` demands journal state `recovered` (`retained_state.cpp:708-711`), unreachable without process restart. Restart does recover correctly. Whether an in-process reconciliation route is required is a spec question, not a proven defect.

## Things verified sound within scope

- Dependency/parent/planned-membership validation occurs against the candidate snapshot before any write and identically during replay (`apply` reused by `append_impl` and `rebuild`); invalid batches are never swapped in, and their sources stay unpublished (`rebuild` discards the candidate on `invalid`).
- `reject_recovery_batch` is allocation-safe (reserved vectors, combined size bounded by `max_records` from scan), rewrites the cursor to the valid prefix without truncating bytes, and forces `blocked` after `confirm_recovery` via `recovery_.problem`.
- Dispatch consumes permission (retained `attempt-open`) before the adapter call; reentrant dispatch sees `opened` and no-ops; `EffectIntent.input` is a view into a dispatch-local owned copy of the admission, so reentrant mutation cannot invalidate it.
- Recovery fencing: staged facts publish only after a new full sync (`confirm_recovery`), verifier precedes `resume_after_reconciliation`, and recovered admitted/open attempts can never dispatch (evidence ≠ live) even after reconciliation.
- Issuer counter monotonicity, wrap refusal, and uncertainty burn through `max(pending_counter_, visible().counter)`; the new codecs have exact-byte vectors, full truncation sweeps, reserved-field/kind/range rejection, and allocation-failure cases. `ErrorCode::audit_unavailable` is the maximum, so the codec range checks are correct.
- Crash test uses real SIGKILL at both specified cut points with exact expected effect bytes and a signal-status assertion — valid process-crash evidence as claimed.

## Verdict

Within the declared U1 bounds (root only, no continuation/namespace-entropy/emergency controls, synchronous single custodian), the component is **not yet correct as implemented**: B1 breaks the stated heap-failure invariant and can permanently suppress an admission on a healthy writer, and B2 breaks guaranteed conflict retention at legal sizes. Both are small, localized fixes. After those fixes and after adding the missing oracles (pre-I/O-failure resubmission, torn-reservation burn, observation/receipt transition matrix, rejection-at-batch-limit boundary), the root owner can be considered correct within the stated bounds; the remaining items are clarifications, not blockers.
