## B1: withdrawn — my premise was factually wrong

I re-read both paths. `FramedJournal::append` wraps *all* allocating work (encoding reserve/insert, `encode_journal_frame`, commit encode, `prepared` reserve/push_back) in the `try` at `src/journal_writer.cpp:237` whose `catch (const std::bad_alloc &)` at 297 **returns** `Result::failure`; nothing after the catch allocates, and the pre-try validation section (207–236) performs only arithmetic on spans. A bad_alloc during a test double's `synchronize` (the only post-write allocation, e.g. `MemoryFile::synchronize`'s copy) occurs after `AppendAttempt` construction (line 276) and therefore poisons the journal — the intended uncertain path, which `append_impl` correctly preserves by *not* resetting `prepared_`. On the RetainedState side, every allocation in `append_impl` that can throw before `prepared_` is assigned (encode loop, `candidate` copy, `retain_rejection`) leaves `prepared_` untouched, and `prepared_ = std::move(candidate)` itself is a non-allocating move. I cannot construct a realizable trigger where an escaping allocation leaves a stale `prepared_` on a live journal. **B1 is withdrawn.** The new sweep oracle (`tests/retained_state_test.cpp:516-524`: resubmit at every no-write/live cut, require `existing==false`, `evidence==live`, 3 committed facts, exact `acknowledged + 151` synchronized bytes — 32+63 frame + 56 commit, arithmetically correct) is exactly the right regression oracle for the claim and closes the gap I originally flagged.

## B2: my 3.9 KB example was invalid; your 4×978-byte boundary is real; the proposed correction is sound with four required refinements

Confirmed: with `max_payload=1024` a single admission can't reach the boundary, but four 978-byte complaint events fill a 4096 batch exactly (4×(32+978)+56=4096), and a leading changed complaint yields a ~3976-byte proposal whose 4 chunk headers + marker frame + commit exceed 4096. Realizable at legal sizes. Mere budget shrinking would indeed still silently drop rejections, so I agree it doesn't satisfy the claim.

The new sub-plan paragraph (lines 176–182: preflight all lengths/references/record/sequence/file budgets; ordered source-only batches; one dependency-linked marker; marker-only completion; partial failure closes ordinary admission and never reports complete capture) is the right shape and stays within existing mechanisms (source frames + dependency references + the already-specified "empty inline proposal means concatenate dependency chunks"). Confirm it, subject to these amendments before implementation:

1. **Orphaned-chunk replay semantics must be explicit.** A crash between a committed chunk batch and the marker leaves committed, replay-published source chunks with no marker. State that such chunks are retained readable bytes with *no* rejection/conflict semantics, that replay never synthesizes a rejection from them, and that recovery treats a pending/torn marker batch via the ordinary uncertain path. As written, "only the final marker signifies complete retention" covers consumers but not replayer disposition.
2. **Chunk count bound and over-limit terminal behavior.** The marker's dependency list lives in one frame bounded by `max_payload` (24 bytes per reference), so maximum retainable proposal size is `floor((max_payload − marker overhead)/24) × max_payload`. State this bound, and state that a proposal exceeding it is a *preflight* failure (nothing written, admission unaffected, loss reported explicitly) — distinct from post-write failure, which closes admission. The paragraph currently only describes the post-write case.
3. **Synchronous completion within the call.** Retention must finish (or fail) before the original `conflict` result is returned, so the sequential custodian never interleaves unrelated submissions between chunk batches and the marker; preflighted chunk sequences then remain exact. Worth one sentence.
4. **Marker semantics for both envelope kinds.** State that the same multi-batch form serves `IdentityConflictEvent` (empty inline proposal) and `RejectedSubmissionEvent`, since the motivating case can be either.

Required oracle when implemented: the exact 4-complaint/3976-byte history; verify per-batch exact bytes and sequence references (including that chunk sequences skip intervening commit frames), marker dependency order, conflict result returned only after the marker's sync, plus a SIGKILL cut between chunk batch 2 and the marker asserting chunks readable, no rejection inferred, recovery clean, and admission state as specified.

## Clarifications: assessment

1. **Nonterminal observations retained, not deduped** — accept; consistent with observations having no identity field, and the terminal special-case dedup remains justified because a second terminal is a transition violation anyway. No code change needed.
2. **Within-batch changed identity → IdentityConflict** — endorse; the change is `existing(committed_, …)` → also checking the candidate at `retained_state.cpp:472`. Add the oracle: two same-ID/different-actor decisions in one batch → retained `IdentityConflictEvent` referencing a proposal containing both encoded events.
3. **Fresh retry decision per retry of a given invocation** — endorse; implement as rejecting a `RetryEvent` whose `(decision, invocation)` pair already has a retained retry, regardless of attempt. One decision planning retries of *different* invocations stays legal. Add the reuse-rejection oracle.
4. **In-process result-recording failure → U1 continuation path** — accept; consistent with "no silent resume of an incomplete audit." Note this makes in-process recovery unreachable until continuation lands, so the sub-plan should state that restart-recovery is the interim route — otherwise fine as a declaration of intent, not an implemented claim.
