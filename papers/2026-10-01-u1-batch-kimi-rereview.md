# Rereview: U1 physical batch writer — verification of F1–F9 resolutions

**Scope (read-only; nothing executed by me):** reread `src/journal_writer.cpp`, `tests/journal_batch_test.cpp`, `tests/journal_crash_test.cpp`, and the supplied `context/u1-events-batch-debug-second.log` (8/8 passing on arm64 Mac debug — reporter-supplied, not my execution). Codec, native storage, foundation, and the new `retained_events` semantic codecs are outside this rereview per the brief; `journal_writer.hpp` was unchanged in the described deltas and was not re-read in full. The release/ASan and Neuroses lanes are running independently and are not claimed here.

## Disposition of prior findings

**F1 (oversize on-disk length misclassified) — Resolved.** `scan()` now reports `ErrorCode::corrupt` for a length field exceeding the declared header limit (`journal_writer.cpp:327-329`), with an exact oracle: byte 136 (first frame's length field, offset 112+24) set to 39 against `max_payload=38` yields a `corrupt` recovery problem (`journal_batch_test.cpp:408-413`). The standalone codec keeping `capacity` for caller-selected limits is a coherent boundary split. Verified correct: the scan pre-check fires before `decode_journal_frame`, so the corrupt classification is the one observed.

**F2 (zero-progress write untested) — Resolved.** `zero_progress`, `impossible_write`, and `interrupted_sync` are now all exercised (`journal_batch_test.cpp:330-354`), asserting `io`/`interrupted` errors, `poisoned` state, empty records, and untouched bytes. This also covers the F6 sync-interruption part.

**F3 (no multi-frame batch) — Resolved.** `multi_frame_and_open_bounds` builds a two-frame batch under `{38,126}` limits: total 2×35+56 = 126 exactly equals `max_batch_bytes` (a true boundary, not slack), `end_offset==238`, `sequence==3`, commit `first==1` at byte 214 and `count==2` at byte 222 are independently derived from the layout, and a three-frame append (161 > 126) is rejected as `capacity` with no writes and `live` state preserved. I traced the append budget check (`journal_writer.cpp:225-232`) and the scan batch bound (`:352`) by hand: both accept 126 and reject 161 correctly. Recovery re-stages both frames with sequences 1 and 2. See R1 below on the hardcoded CRC constant.

**F4 (pending records unasserted) — Resolved.** The cut loop now asserts `pending_records().size() == (end >= 147 ? 1 : 0)` and reads the pending payload back to `original` (`journal_batch_test.cpp:243-247`); the crash suite asserts the same at threshold 238 with a payload read (`journal_crash_test.cpp:213-218`). I verified both thresholds against the layout: in the batch test the first source frame completes at 147; in the crash test the second source completes at 238, and cuts 235/236 correctly yield zero pending (header complete at 235 but the 3-byte payload length exceeds remaining bytes → `incomplete` before decode).

**F5 (no OOM oracle) — Resolved.** A global `operator new` cut (`journal_batch_test.cpp:17-30`) sweeps cuts 0–31 through `append`, asserting: pre-write failures leave state `live`, zero write delta, and byte-identical storage; post-write failures poison; all failures are `allocation`; the sweep terminates in a successful commit. The single-shot `fetch_sub` design fires exactly once, and post-append CHECKs run after the cut is disarmed, so test-harness allocations can't consume the cut. First-allocation failure in `create` and `open` is separately asserted with no file created and zero writes (`:420-432`). The bad_alloc surface I identified (encode vectors, `MemoryFile::submitted.resize`, the new snapshot copy in `synchronize`) all lands inside `append`'s try block and converts to `allocation` with correct live/poisoned partitioning. See R3 on the sweep bound.

**F6 (read-side short/EINTR, sync EINTR) — Resolved.** Chunked reads (`max_read=2` and `3`) plus injected read interrupts are exercised through both `read_payload` (`:195-198`) and full open+scan (`:377-384`); `zero_read` makes `open` fail `incomplete` via the zero-read mapping in `read_exact` (`:415-418`, code at `journal_writer.cpp:179-181`). Interrupted sync poisons with the `interrupted` code preserved (`:347-354`), matching the spec's unknown-durability rule.

**F7 (open-time identity/header/scan bounds) — Resolved.** Wrong environment → `wrong_environment` (`:386-389`), changed limits → `conflict` (`:390-393`), file larger than `max_file_bytes` (238 > 237) → `capacity` (`:394-395`), 64-byte file → `incomplete` (`:396-398`), and scan-side `max_records=1` exhaustion against a two-record journal → `capacity` recovery problem, empty staged, `blocked` after confirm (`:400-406`). All error-code paths verified against `journal_writer.cpp:139-143,155-160,372-375`; the `std::optional<Error>` comparisons match on default `detail=0`.

**F8 (no creation crash cuts) — Resolved.** `creation_crash` covers write cuts at 0/60/111/112, before/after file sync, before/after directory sync, and after return, with the child armed from the start (`journal_crash_test.cpp:230-276, 289-296`). Oracles: recreation always `conflict` (native O_EXCL), sub-112 extents fail `open` as `incomplete` (never a fresh journal), a full-header survivor opens `recovery_pending` with cursor (0,112), refuses append, and reaches `recovered`; the file is never modified by recovery. Cut semantics verified against `CrashFile::write_at`: cut 0 crashes before any byte; 60/112 crash exactly when the partial/full write completes. The new directory-sync ordering assertion (`journal_batch_test.cpp:159`, `CHECK(submitted == synchronized)` inside `synchronize_directory`) genuinely pins file-sync-before-directory-sync in both `create` and `confirm_recovery`.

**F9 (no positive resume oracle) — Resolved.** The `end == 112` clean-cut branch now requires `resume_after_reconciliation()` to succeed (`journal_batch_test.cpp:251-253`).

**Snapshot preservation fix — Verified.** `MemoryFile::synchronize` now copies-then-swaps (`journal_batch_test.cpp:126-127`), so a `bad_alloc` during the snapshot leaves the previously acknowledged `synchronized` set intact; the old direct copy-assignment could indeed have destroyed it. The throw path is reachable under the allocation sweep and converts to `allocation` with poisoned state, as analyzed in F5.

## Residual items (all minor; none block)

- **R1 — CRC constant anchored indirectly.** The two-frame batch CRC bytes `{106,248,236,195}` (value 0xC3ECF86A LE) at `journal_batch_test.cpp:369-370` cannot be hand-recomputed (560 table steps); its correctness rests on the implementation agreeing with the separately reviewed codec, whose own independent `123456789` → 0xE3069283 vector anchors the CRC itself. The verification chain is sound but one link is execution-witnessed, not reviewer-derived.
- **R2 — allocation sweep bound is empirical.** The `cut < 32` sweep assumes the append path performs fewer than 32 allocations (I count ~17–20: two reserves, two frame vectors, ~12 growing resizes across the 13 seven-byte write chunks, one snapshot). Future code adding allocations could make `finished` fail spuriously — a safe failure direction, but worth a comment. The override also lacks aligned `operator new` overloads; harmless today (no over-aligned types), it would silently bypass the cut if one is introduced.
- **R3 — no crash cut during `confirm_recovery`'s own syncs.** The crash suites cut create and append syncs, but the child always confirms recovery before arming (`journal_crash_test.cpp:183-185`). A SIGKILL between `confirm_recovery`'s file sync and directory sync is unobserved; the expected aftermath equals an already-covered clean-reopen case, so the marginal value is low, but the plan's "enumerate cuts at … sync/publication" arguably includes it.
- **R4 — semantic-kind drafts still untested** in the batch path (only `source` used). Frame handling is kind-generic and semantic validation is RetainedState's explicitly unfinished work, so this is cosmetic; a one-line second draft with `FrameKind::semantic` would close it.
- **R5 — sequence `UINT64_MAX` budget path** (`journal_writer.cpp:217-219`) remains review-only; hand-verified boundary correct, practically untestable.
