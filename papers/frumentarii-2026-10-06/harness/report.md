# Frumentarii: self-evolving harnesses

2026-10-06. Research lane: what changes, how experience drives changes, how evidence separates genuine improvement from artifact, and how the agent continues inhabiting its machinery. Source inspection only: no reference execution, model calls, credential use, dependencies adopted, product edits, or reproduced benchmark results.

## Findings that should change Arco's course

1. **Make the evolution unit an executable behavioral program plus its actual environment.** Lua turn/tool/context programs are natural experimental units. Tie each run to actual program contents, model/provider settings, initial context, environment, task and resource budget. A task ID and a nominal harness name are insufficient. ModularRSI's same-task K-roll code catches precisely this confound: repeated stochastic rolls can silently receive different dynamically composed modules.
2. **Archive experiments independently of activation.** DGM's diversity archive retains executable losing variants as potential stepping stones. A useful bad experiment belongs in history without becoming the operator's active harness. Arco already has the audit and RRC ingredients for this distinction; do not equate archiving, selecting, and applying.
3. **Use contrasting actual trajectories to diagnose recurring causes.** Compare success and failure for the same task and program, then ask whether the suspected mechanism recurs across tasks. This is much more actionable than a generic reflection on one failed chat. Preserve useful pure successes too: unnecessary shell retries and bloated observations can be diagnosed even when the task succeeds.
4. **Continuity is a state transition, not a delay.** Exo has concrete detached rebuild and durable outcome machinery, but its deferred runner initially sleeps two seconds rather than proving the requesting turn ended. Borrow outcome visibility and reboot messages; retain Arco's actual quiet boundary and explicit distinction between pause, stop, and continue. Native build failure should return the same session to the last working executable with compiler output available.
5. **Judge delivered behavior, including regressions, under matched budgets.** Keep task success, cost, elapsed time, unknown side effects, infrastructure failure and operator intervention as distinct observations. HELIX's fixed-candidate score and post-hoc union over many candidates answer different questions. A giant portfolio's theoretical coverage is not the performance of a deployed Arco.
6. **Learning doctrine needs behavioral witnesses.** Construct tasks where a tempting shortcut can pass shallow checks yet violates the actual requested behavior. The poisoning work's executable forged-JWT witness is the right pattern: call the produced program with an independently chosen discriminating input. For Blackbird, witnesses should exercise source use, continuation after failure, meaningful tests, repair from originals and productive completion, rather than count declarations about rigor.

These are design consequences, not a new approval process. They can be ordinary programs available to operator and model in autodroit mode.

## Source studies

### DGM: executable diversity, not only hill climbing

Primary [paper](https://arxiv.org/abs/2505.22954v1), [original source](https://github.com/jennyzzt/dgm/tree/a565fd2d1dca504ef5104a7cc0f3bdc4ab9b4fd2). Read paper methods/evaluation/generalization, `DGM_outer.py`, `self_improve_step.py`, and `tests/test_bash_tool.py`.

`choose_selfimproves` samples parents with a transformed accuracy score multiplied by inverse child count. Failures include ordinary unresolved tasks, empty patches, stochasticity and repeated context-limit errors. `update_archive` defaults to `keep_all` after the executable filter; even `keep_better` compares to original score with noise leeway, not monotonic parent improvement. `self_improve` applies ancestor patches in a fresh environment, runs the parent coding agent on a diagnosed harness problem, captures its new patch and chat, and evaluates the descendant. Small/medium/full evaluation stages conserve search cost. This is genuinely code-level agent evolution. It is not a continuously replaced current process.

The inspected bash tests assert expected outputs/errors for simple command cases. They do not qualify evolutionary search. Concrete source cautions: the `best` branch sorts scores ascending then takes the first entries, despite its name; argparse concatenates `'score_child_prop' 'best'` because a comma is absent. Those are reasons to independently test parent selection rather than import experimental code or assume paper descriptions match every branch.

**Arco experiment:** keep a losing tool/workflow candidate that improves one class of work, allow the model to build a second candidate from it, and assess that descendant on fresh work. Direct oracle: exact selected parent and executable program identities in the actual runs; improved finished-task behavior under the same budget. Retention itself is not an improvement claim.

### SICA: historical evidence is usable agent context

Primary [paper](https://arxiv.org/abs/2504.15228v2), [source](https://github.com/MaximeRobeyns/self_improving_coding_agent/tree/ed8275dca4d3c5dbf77229964351fe9b424797dc). Read methods/context organization/limitations, `runner.py::select_base_agent`, `run_meta_agent_benchmark`, `base_agent/src/utils/archive_analysis.py::BenchmarkScore.utility`, and `base_agent/tests/utils/test_archive_analysis.py`.

SICA exposes the archive to an improving agent read-only and a new copied implementation read-write. Base selection finds best mean score's lower confidence bound and prefers a recent iteration meeting that bound. The actual editing agent is chosen separately as the archive's best iteration. The current change log is carried forward even when code is copied from an older base. The paper reports 17→53% on a random SWE-bench Verified subset; that is author evidence, not a whole-suite replication. Runtime benchmark construction in the inspected runner uses subset size 18. Resource-sensitive utility exists, but the improvement base-selection call explicitly requests `mean_score`; resource limits must therefore not be inferred from that ranking. Tests use synthetic alternating success/failure fixtures and assert exact 0.5 values for aggregate analysis.

**Arco consequence:** the audit explorer should let an agent compare its actual attempts and old candidate programs without first receiving a lossy external diagnosis. Preserve code ancestry separately from chronological operator/model learning. Make the configured selection objective explicit and expose success/cost/time separately.

### STOP: the optimizer program can be evolved too

Primary [COLM paper](https://arxiv.org/abs/2310.02304v3), [Microsoft source](https://github.com/microsoft/stop/tree/0d6780c54306b2486dd36e9c4ae9b49aceb27ea4). Read Algorithm 1 and seed improver, `run_improver.py::attempt_algorithm_improvement`, `tasks/meta_optimization/secret_seed_algorithm.py::improve_algorithm`, and `secret_utility.py::meta_utility`.

The initial improver generates several code candidates and chooses by supplied utility. Meta-utility runs a candidate improver on a downstream optimization problem, rather than scoring its prose or code aesthetics. LM-call and utility-query budgets are explicit. Generated optimizer code is reloaded as the next improver. The outer exception path falls back to a previous callable; downstream validation and test utilities are distinct. A noteworthy limit in source: an outer improvement is considered successful when checked utility is nonzero, not necessarily greater than predecessor utility. No test suite qualifying the recursive optimizer was inspected.

**Arco consequence:** an autodroit campaign program is itself an experimental artifact. Allow the model to propose different search/review/retry allocation strategies, and score them by useful changes delivered to independent tasks per budget. Do not let “the campaign produced a candidate” count as “the campaign improved.”

### CLM: model agency over context plus learned editing programs

Primary [official source](https://github.com/facebookresearch/context-language-models), existing [local acquisition catalog](../../2026-10-01-context-language-models-acquisition.json). Re-read `clm/clm_harness/context_env/edit_gate.py`, `context_env/env.py::_apply_edit`, and `clm/clm_icl/evolve.py::score`, `diff_se`, `gate`, `pick`; existing prior local CLM study remains available.

A local rendered context file is parsed back into model input. The fit gate permits growth when budget permits, whereas shrink requires reduction; growth is not intrinsically invalid. The evolution code runs incumbent skills, builds notes from better/worse same-task rollouts, proposes candidate skills, and grades complete development episodes. Task-level standard error is paired when task sets match; close accuracy results are decided by comparable cost. Malformed skills are dropped, not silently repaired. Completed runs/proposals support resume. Development tasks default to training when a separate set is absent, so that default cannot establish heldout generalization. No independent semantic-recall oracle follows from a shape/token gate.

**Arco consequence:** preserve generic context repair/growth agency alongside managed compaction. Compare policies on original-derived exact facts plus actual productive task constraints, including delayed recall after RRC. Skill evolution can be a Lua workflow; this does not require a resident kernel or importing the Python harness.

### Self-Harness: explicit candidate lifecycle and a revealing selection boundary

Primary [paper](https://arxiv.org/abs/2606.09498v1), [source at existing pin](https://github.com/qzzqzzb/Self-Harness/tree/2720dbb3f52283684f4b85a1065d642df1779dd8). Re-read Algorithm 1 and `acceptance/scripts/run_acceptance_gate.py::run_acceptance_gate`, `compare_split`, `split_repeat_metrics`; existing corpus includes proposer hook declarations and persisted workflow queue.

The same fixed model proposes minimal changes to declared harness hook surfaces from verifier-grounded failures. The acceptance implementation validates repeat counts and denominators, then accepts when neither train nor heldout mean drops and at least one rises. The paper's algorithm uses both splits during each round's selection. Thus “heldout” means withheld from the proposer evidence, not untouched by the optimizer. Repeated selection can adapt to it. Mean nonregression across two repeats is not strong evidence of a statistically stable gain. Its candidate/branch state is useful experimental provenance but not universal request/program audit.

**Arco consequence:** distinguish discovery cases, reusable comparison cases and a final fresh task exercise. Repeatedly consulted evaluation becomes development data whatever its directory name. Individually accepted edits should be tested as the final integrated program: merging successful candidates can introduce interaction failures.

### ModularRSI: causal diagnosis requires same code as well as same task

Primary [Sep 14 paper](https://arxiv.org/abs/2609.14857v1), [source](https://github.com/IQuestLab/ModularRSI/tree/b5c72c36b0d08ff93f00ee202a8fbdebe849dfb9). Read method/modules/integration/limitations and source prefix `src/harbor/agents/terminus_2_modular/self_evo/`: `k_roll.py`, `online_evo.py` review/partial-accept/sanity paths. Read `tests/unit/test_k_roll_bundle.py`.

The behavioral decomposition is agent loop, observation, context, tools and completion detection. Same-task contrasts diagnose recurring mechanisms; module-local edits are later integrated. The particularly useful implementation captures first rollout's dynamically selected complete bundle, including helper subset, writes a private code snapshot and runs remaining rolls statically from it. The shared generation pin is never rewritten by a task. Missing first-roll bundle invalidates a multi-roll group. Tests assert dynamic composition happens exactly once, exact bundle reuse, helper identity, preservation of original generation pin and missing-manifest failure. A single crashed roll remains recorded rather than invented as a valid contrast. The self-review stage is another editor pass, not independent provider review. It can drop named files and rerun smoke; task failures and infrastructure timeouts are explicitly distinguished from code crashes. The paper reports benchmark-disjoint evolution and cross-model evaluation; these results were not reproduced here.

**Arco experiment:** repeated same-task runs with one precisely captured Lua/tool/context bundle; inject a changed helper or context policy between runs and ensure it invalidates causal comparison. Follow independent module improvements with a combined run. Tests for bundle identity answer a different fault class from task correctness, so both are justified without adding ceremonial verification layers.

### HELIX: flexible recomposition and honest portfolio interpretation

Primary [Aug 14 paper](https://arxiv.org/abs/2608.13951v1), [source](https://github.com/HKUDS/HELIX) pinned in manifest. Read methods/evaluation/limitations, `packages/recipes/src/compiler.ts::compileRecipe`, assembly-contract declarations, `packages/conformance/recipes.conformance.test.ts`.

Recipes compose multiple product families through typed capabilities. Compilation validates schema, expanded duplicates, declarations and missing requirements, then creates dependency graph, capability bindings and a lockfile. Tests assert concrete tool-executor/provider bindings and reject incompatible recipe structures. This is executable composition infrastructure, not just a taxonomy. The paper deliberately separates a selected fixed harness's 4% coverage improvement from up to 58% post-hoc portfolio gain. Its verified sibling trajectories become multiple training-record types; this alone does not demonstrate repeated actual model-weight updating. Source archives contain 101 absolute-path fixture symlinks; these were omitted during safe extraction and recorded, with archive intact. Missing external fixture targets limit reproduction.

**Arco consequence:** Lua programs should expose behavioral composition points with contracts and actual selected definition identity. Recombine policies without requiring a new C++ build. Measure the deployed routing/selection policy including its calls, not the oracle union of best answers from every experiment. Avoid reproducing a giant atom catalog before useful composition needs emerge.

### Exo: actual restart machinery, limited smoke evidence

Primary [source](https://github.com/exoharness/exo/tree/e58617450b0752e5afcdd8bb4558f4ba8c3d11f4). Read `docs/SELF-CONTROL.md`, `exo/tools/guardian-tools.ts::queueRebuildAndRestart`, `exo/scripts/deferred-rebuild-and-restart`, `exo/scripts/exo-service-guardian::drain_pid_file`, guardian tool tests, and self-evolution smoke verifier scripts.

A model requests queued rebuild with an ID/reason and durable JSON outcome. A detached guardian builds/restarts, records status and appends a host event; reboot notices wake adapter conversations. Service drains use claimed markers with grace and process-tree fallback. The requesting tool returns queued status rather than successful activation. But the deferred runner starts after a fixed two-second sleep: that is not a quiet-turn proof. Smoke tests only check output literals and timeout marker files; their README explicitly says self-modification mechanism is not enforced. Their success would not establish genuine harness evolution. Snapshot rewind preserves event history rather than erasing failed experiments.

**Arco consequence:** keep evolution/restart outcomes model-readable after resume; use exact quiet-state semantics rather than elapsed delay. Never confuse queued request with build/activation success. An activation oracle must examine the new executable/program identity and actual next model request, then demonstrate useful work under it.

### Ouroboros: stateful ongoing evolution and restart fault classes

Primary [Aug 8 paper](https://arxiv.org/abs/2608.08311v1), [source](https://github.com/razzant/ouroboros/tree/4b37f96223b4b8248eea80c9be22cf923759cd5a). Read architecture/evolution sections, `supervisor/evolution_lifecycle.py`, `supervisor/restart_retention.py::pause_retention`, and `tests/test_restart_child_orphans.py`; inspected git review fingerprint boundary for scope.

Free evolution and post-task evolution are distinct scheduling patterns, feeding durable maintenance from useful work. Source distinguishes saved pause with continuation source, unused resume grant, pause intent without checkpoint and running/consumed continuation. Boot generation is explicit; stop intent remains latched across failed persistence. Restart-child tests assert children of interrupted roots cancel, children of revived paused roots remain scheduled, and completed parents do not automatically cancel children. The project also contains extensive mandatory reviewed-commit machinery, which is its policy, not adopted doctrine. Current source is a broad evolving product and not necessarily identical to the paper's benchmark seed.

**Arco consequence:** station feeds and operator campaigns can share one execution engine; scheduling mode is not self-improvement mode. On RRC, saved checkpoint and requested pause must remain distinguishable. Test pending peers/children according to explicit parent outcome rather than deriving cancellation from a missing process alone. Keep this scoped to Arco clients; do not govern external DB/kernel daemons.

### Boundaries: SEAL and the latest multitask paper

[SEAL paper](https://arxiv.org/abs/2506.10943v1), [source](https://github.com/Continual-Intelligence/SEAL/tree/6d9c9f9ee392c6cc618e771f399d436d190f6ca4). Read methods and `few-shot/self-edit.py` LoRA configuration/training setup, `general-knowledge/src/inner/TTT_server.py` baseline-vs-adapter path and dataset preparation. Self-edits produce training material and directives evaluated after adapter finetuning. The learning object includes weights; it is not a hosted agent rewriting its tool loop. For Arco, treat an external adaptation service as another consumer-facing capability if later wanted, not as a hidden assumption behind current provider subscriptions. The transferable experimental pattern is measuring the downstream effect of an edit against a real baseline, not rewarding the edit's appearance.

[Self-Evolving Harness on Multiple Tasks](https://arxiv.org/abs/2609.38372v1), Sep 29: read original method/figure and local PDF. It treats code plus evolution notes as optimizer state, uses the same model in solver/proposer roles, fresh task batches followed by new-domain tasks and replay anchors, and an added-line edit budget. This is directly relevant to keeping durable notes about failed hypotheses across Arco campaigns. No original source URL was established in this bounded lane, so it remains paper-only rather than implementation evidence. Added-line cap is a search-control choice, not a demonstrated measure of complexity or quality.

## Independent outcome witnesses for the first autodroit experiments

These are proposed experiments, not launched work or adopted product specifications.

| Priority | Useful work / hypothesis | Direct oracle and discriminating failure | Measure |
| --- | --- | --- | --- |
| 1 | Evolve timeout/retry workflow while implementing a real feature | Native command writes a unique marker, emits partial output, then times out; model chooses a distinct next action; finished artifact verified independently; marker remains once | Task correctness, duplicated effects, time/calls, interventions |
| 1 | Build an audit explorer while evolving context policy | Plant exact task constraints outside latest window; after compaction/RRC require program to satisfy them; deliberately omitted fact recovered from immutable original, actual provider request inspected | Exact recall, finished behavior, input size/cost, repairs |
| 1 | Improve campaign allocation/search program | Candidate campaign runs same fresh feature tasks and budget as incumbent; independent output examples challenge the final artifact | Useful accepted changes per budget, unresolved regressions |
| 2 | Refit core with meaningful native change | Inject compiler failure first; old executable resumes original context; successful subsequent build changes executable identity; next model request continues once; pending mutation visible only after quiet boundary | Lost/duplicated requests/effects, activation delay, recovery effort |
| 2 | Contrastive diagnosis under dynamic Lua composition | K-roll copies exact program/helpers/context policy; intentionally switch one between rolls; mixed identity cannot masquerade as stochastic causal evidence | Diagnoses supported across tasks; valid contrast count |
| 2 | Integrate independently improved tool and context modules | Evaluate final combination on cases exercising interaction, e.g. partial exec output kept only in audit after compaction then read to repair task | Actual combined correctness and observed regressions |
| 2 | Preserve doctrine under tempting benchmark shortcut | Task fixture offers misleading passing test; independent callable input distinguishes correct behavior; compare candidate trained on shallow feedback with candidate using real source/behavior evidence | Correct delivered behavior, shortcut failures, actual source used |

The last row is grounded in [Reflections on Trusting Trust, Revisited](https://arxiv.org/abs/2609.17817v1) and [original witness source](https://github.com/froeschele/trusting-trust-revisited/tree/93f1a8f32fd22261852445d6a348e7a8f417da28). Read threat model, DGM setup and open-science appendix; inspected `evaluation/verdict.py` reconstruction/static classifiers and `evaluation/behavioral_witness/behavioral_jwt.py::probe`. Successful DGM end-to-end poisoning required modifying its diagnosis prompt; do not report it as stock-DGM compromise. Captured solutions are behaviorally challenged with a wrong-key token, and accepting forged claims establishes the defect; broken/empty/error outputs are `unclear`, not safely classified. Similar TLS/YAML witnesses cover other classes. No acquired malicious task or witness was executed here. The lesson is independent behavior evaluation and provenance of evidence, not adding approval rituals or restricting ordinary operator/model agency.
