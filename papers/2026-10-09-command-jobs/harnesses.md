# Running command jobs: harness implementation study

2026-10-09. Read-only source study for the operator's command background / foreground priority. No acquired implementation was executed, changed, or selected as a dependency. Tests below were read, not run. Claims concern the retained revisions, not today's upstream heads. Source paths are relative to this repository; GitHub links bind the same revisions. Literature and Blackbird's present implementation are separate research lanes.

## The central distinction

Three operations commonly share the word foreground: waiting for a result in a model tool call, focusing a terminal for operator interaction, and transferring the actual controlling terminal foreground process group. They have different consequences. Harness backgrounding normally releases a waiter or display while a persistent owner keeps the same process and I/O alive; it does not send SIGSTOP. Reattaching a view, waiting again, or routing input to that process does not require launching the command again. A shell's `fg`, conversely, operates on its own jobs/process groups and terminal. A Blackbird design must name the semantics it supplies.

Of the inspected harnesses, Codex provides repeated model waits/input on one process; Gemini provides selectable, focusable views/input on previously backgrounded PTYs; Qwen explicitly hands a running foreground command to a background registry but does not expose a corresponding shell foreground API in the inspected implementation; Kimi launches distinct detached background workers with output files; oh-my-pi makes a command a managed job from inception and releases its foreground wait; Hermes adopts an already-running pipe process. None of these is a complete ready-made Blackbird design. Their strongest common mechanism is separating job lifetime from the observer/waiter lifetime.

## Codex: persist the owner before the first wait

Implementation: `quarantine/codex/codex-rs/core/src/unified_exec/{mod.rs,process.rs,process_state.rs,process_manager.rs,async_watcher.rs,head_tail_buffer.rs}`; low-level lifecycle in `codex-rs/utils/pty/src/{process.rs,pipe.rs,pty.rs,process_group.rs}`. The core manager owns a map of process IDs to `Arc<UnifiedExecProcess>` plus permission/environment/original-call metadata. Each process owns transport handle, output producer, exit state, output buffers and a per-process interaction lock. Local pipes and PTYs and remote exec-server transports converge on that abstraction.

`exec_command_inner` stores a live process before waiting for the initial yield (manager lines 595–629). The explicit reason is that cancelling the turn must not drop the last owner and thereby terminate the background process. The caller gets output plus process ID when still alive; subsequent `write_stdin` polls that exact process. A yield deadline is a wait deadline, distinct from a completion-only command's execution timeout. Initial yield is clamped to 250–30,000 ms, with a Windows 10-second floor. Empty follow-up waits use a configurable 5-second minimum and default 300-second maximum; input-bearing waits cap at 30 seconds. Non-TTY commands reject ordinary stdin; a special Ctrl-C operation becomes a signal. TTY input is sent through the same process writer. This is useful evidence for explicitly describing pipe versus PTY capabilities to models.

`write_stdin_inner` (lines 883–979) captures the original process, locks its interaction mutex, then checks map membership and pointer identity again. After any approval await it revalidates identity once more. Different jobs may be interacted with concurrently; one job's draining reader, writes and lifecycle do not overlap. This prevents a queued operation aimed at a removed/reused numeric ID from reaching its replacement. Blackbird needs the identity principle even without Codex's approval system.

Output is not an immutable full transcript: `OutputBuffers` atomically appends each chunk to both a pending buffer and a retained transcript, each using a 1 MiB head/tail bound and omission counts. The poll collector drains pending with `mem::take`; its aggregate stays bounded across many drains. UI broadcast deltas are a separate path with 64 channel entries, an 8 KiB per-event bound and a per-call delta limit. Broadcast lag is skipped; this UI transport is not the authoritative transcript. The combination is appropriate for bounded model summaries, but preserving full originals requires a different archive underneath. A cancelled collector can lose its locally drained response snapshot even though transcript retains bounded evidence; do not equate this destructive poll protocol with independently replayable consumer cursors.

Exit and output close are tracked separately. The collector waits for both when possible, but its post-exit close wait is bounded to 50 ms. The streaming watcher allows 100 ms trailing output. This prevents indefinite waiting when descendants retain output descriptors, but makes returned terminal output a bounded-drain observation rather than proof that every writer closed or every future byte was captured. Later `refresh_process_state` removes exited entries. Blackbird must define whether direct-child exit seals output, whether descendants remain owned, how incomplete drain is represented, and whether a completed job remains inspectable after its last wait.

The manager caps entries at 64; pruning protects eight most recently used jobs, prefers exited entries outside that set, then takes an older live job and terminates it. That is a consequential policy, not merely memory management. An explicit capacity refusal or operator-directed eviction would avoid silently killing useful live work. `terminate_all_processes` drains the registry, cleans approval metadata and terminates handles. Low-level `ProcessHandle::Drop` terminates and aborts readers/writer but detaches the waiter so a terminated child can still be reaped. Pipe spawn detaches from the controlling terminal; Unix process-group helpers use group signals, Linux parent-death SIGTERM and an immediate parent-PID recheck; macOS denied group signaling has member fallback. These process-group mechanisms do not automatically capture a descendant that starts a new session.

Tests inspected:

- `core/tests/suite/unified_exec.rs::unified_exec_interrupt_preserves_long_running_session`: child writes its PID before `exec sleep`; test waits for that artifact, interrupts turn, uses OS liveness to establish survival, then cleans background terminals and waits for actual exit. It tests ownership, not only returned text.
- Same suite: `unified_exec_keeps_long_running_session_after_turn_end`, `unified_exec_reuses_session_via_stdin`, `write_stdin_returns_exit_metadata_and_clears_session`, `write_stdin_calls_run_in_parallel_across_sessions`, early-exit notification and lagged-output cases. They define tool-facing lifetime and actual follow-up behavior.
- `process_manager_tests.rs::output_collection_stays_bounded_across_repeated_drains`: handshakes each producer chunk with drain, compares both aggregate output and retained transcript to the declared head/tail policy. Useful boundedness case, but its expected value uses the same buffer implementation, so an independent byte-selection oracle is stronger.
- The same file's omission-preservation and pruning cases; `process_tests.rs` remote unknown-process/closed-stdin/termination-failure cases; low-level pipe/process-group tests.

## Gemini: backgrounding settles a waiter; terminal focus returns to the same PTY

Implementation: `quarantine/gemini-cli/packages/core/src/services/{shellExecutionService.ts,executionLifecycleService.ts}`; terminal tools in `packages/core/src/tools/shell.ts`; UI in `packages/cli/src/ui/{hooks/useBackgroundTaskManager.ts,hooks/useExecutionLifecycle.ts,components/BackgroundTaskDisplay.tsx}`.

`ExecutionLifecycleService.background` (lines 510–550) resolves and removes the pending result resolver with `backgrounded: true`, null exit code and the output so far. It leaves the execution registered and marks it backgrounded. `ShellExecutionService.background` (1825–1920) keeps the existing PTY/child, starts a log, seeds it from terminal screen or child output, keeps temporary-directory ownership and maintains session history. Repeated background calls do not open a second log. Completion later settles the execution and optionally injects/announces a result. This is not a stop/resume cycle or process relaunch.

The UI establishes an actual operator return path: the background task selector chooses an existing PID; `BackgroundTaskDisplay` resizes the same PTY, subscribes to its existing output, replaces initial history, then appends child-process deltas or replaces PTY screen snapshots. With focus, ordinary key sequences, Enter and backspace route through `ShellExecutionService.writeToPty(activeShell.pid, ...)`. Leaving the view unsubscribes; it does not kill. This is foreground *interaction* while the lifecycle remains backgrounded. It does not reconstruct the original synchronous tool-call continuation.

The snapshot/delta boundary is explicit: subscription synchronously sends current history, then sends live events. Screen snapshots and byte deltas are different representations; terminal emulation supplies reconnect display. Raw-byte archive must be independent of terminal serialization/ANSI stripping if Blackbird retains originals. Gemini's child output buffer is capped at 16 MiB, whereas log streams/history have separate lifetimes. History caps at 100 records and may evict a running entry. Logs use PID-derived paths with exclusive creation. A reused PID or failed log open can preserve execution but lose logging. Logging setup failures are warned, not treated as successful capture.

The lifecycle service's `kill` invokes the execution kill hook and immediately settles its result as aborted. A UI terminal status here is not proof the OS process was reaped. `isActive` can fall back to numeric PID liveness after no registered execution exists, so PID reuse needs attention. These are unsuitable substitutes for a kernel child handle plus observed wait result.

Tests read: `shellExecutionService.test.ts` mocks both PTY spawn and `child_process.spawn`; it verifies same handle's result becomes backgrounded, initial and subsequent bytes are logged, double background opens one stream, temp-dir cleanup, missing session IDs and shutdown cleanup. `executionLifecycleService.test.ts`, `BackgroundTaskDisplay.test.tsx` and `useBackgroundTaskManager.test.tsx` cover lifecycle/selection/focus. Mock callbacks make event-order faults visible but do not qualify actual terminal process-group behavior. The retained `integration-tests/shell-background.test.ts` is an additional field-style test source. Blackbird's own terminal tests should drive a PTY directly and assert child identity, bytes/input effects and focus transitions together.

## Qwen: explicit handoff and the races it must close

Implementation: `quarantine/qwen-code/packages/core/src/services/{shellExecutionService.ts,backgroundShellRegistry.ts}`; `packages/core/src/tools/shell.ts` especially `handlePromotedForeground` (3505 onward); UI Ctrl+B handling in `packages/cli/src/ui/AppContainer.tsx` around 4930. A tagged abort reason `{kind:'background'}` means ownership takeover, whereas cancel/timeout means kill. `promoted: true` is separate from `aborted`, and terminal fields are null while the same child still runs. Reason parsing is defensive so malformed/accessor-bearing values cannot accidentally bypass kill behavior.

The service detaches foreground output/abort listeners and installs post-promote output/settle callbacks; the finalizer registers the background job. It must carry chunks and settlement that arrive between those stages. Preallocated `promoteArtifacts` slots queue chunks and an early settle; the stream is assigned before draining queued chunks to preserve FIFO order. A fresh registry abort controller is necessary: the promote controller is already aborted and cannot later trigger `task_stop`. Registration/directory failures attempt to kill the orphaned child. Stream-open failure records capture loss, disables further buffering, and attempts a snapshot fallback. Disk write failure is material capture uncertainty, not a successful original transcript.

The registry allows exactly one transition out of running to completed/failed/cancelled; late exit callbacks do not overwrite cancellation. Output stream finish/error/timeout handling fences registry completion so observers see accepted bytes after flushing. Separate model copy reports a child that has already exited even while the stream-finishing fence remains pending. Background entries expose an output file, cursor and status metadata; completion notification tails are capped at 8192 bytes and terminal rows at 32. Terminal `task_output` observation is not terminal input reattachment; no inverse foreground shell operation was established in this inspection.

Read tests in `services/shellExecutionService.test.ts` and `tools/shell.test.ts`: promote must not call TERM/KILL, uses same PID, refuses if child already terminal, removes old callbacks, forwards post-promote stdout/stderr with separate decoders, fires settlement once after error plus close, snapshots before append, handles settle-before-register, flushes stream before registry transition, catches ENOSPC, and supplies fresh cancellation controller. These are highly relevant failure schedules. Most are emitter/stream/timer mocks, not real process execution. Critically, a test named “bytes APPEND” inspected around 4377 primarily asserts stream flags and first snapshot write; do not infer a complete byte-conservation proof from its name.

The handoff's implementation complexity argues for Blackbird making every command a job at launch, with one permanent collector/owner and changing only attachment/wait state. This is a design inference, not an upstream guarantee.

## Kimi: detached worker, durable observation, no interactive reattachment

Implementation: `quarantine/kimi-cli/src/kimi_cli/background/{manager.py,worker.py,store.py,models.py}` and `tools/shell/__init__.py`. A background request writes specification/runtime/control/consumer files, launches a worker in a new session with stdin/stdout/stderr DEVNULL, and records worker PID unless the worker already advanced/terminalized the state. The worker launches a *new* shell process in its own session, with DEVNULL stdin and stdout/stderr directly appended to `output.log`. It records child PID/PGID, heartbeats and waits for the shell. There is no adoption of an already-running foreground command, PTY input, or route to turn this worker into an interactive terminal. `TaskOutput(block=true)` waits for the existing worker's status; it does not rerun.

Separate control and runtime files avoid some competing writer problems. Worker TERM→grace→KILL targets the child group. The manager's kill writes requested control and sends a best-effort signal; shutdown calls `kill_all_active`. Recovery rereads stale runtime before recording `lost` or `killed`, using heartbeat expiry rather than claiming an exit status. In-process background agents are marked lost on recovery. This separates evidence of loss from known completion, but heartbeat expiry alone cannot establish process death or safe signaling of a persisted numeric PID/PGID. Time-based transitions use wall clock; recheck narrows a race without making updates compare-and-swap.

`BackgroundTaskStore.read_output` returns bounded bytes with explicit offset/next_offset, clamping requested position to current size. Its `eof` means “at current file size”; a running producer may append immediately afterward. It decodes each read separately with replacement, so UTF-8 split across bounded reads can corrupt presentation even though bytes remain on disk. Worker child completion likewise does not seal the file against descendants that inherited it. These are concrete semantic traps if borrowed without redesign.

Tests read: worker success, kill control and timeout cases run real shell children and assert status/exit/output; manager real-worker tests assert launch/wait and timeout outcomes; store reads assert exact cursor/text slices; manager tests cover launch races, launch failure, stale recovery and notification deduplication. Kill-control tests check state but do not establish that every descendant is gone; Blackbird requires independent descendant liveness and reaping checks for that claim.

## oh-my-pi: one job lifetime, different wait/presentation lifetimes

Implementation: `quarantine/oh-my-pi/packages/coding-agent/src/{async/auto-background.ts,async/job-manager.ts,async/job-control.ts,tools/bash.ts,tools/bash-interactive.ts}` and `crates/pi-natives/src/pty.rs` / `crates/pi-shell/src/process.rs`.

Managed bash is registered before execution with its own abort signal; the job outlives the launching call. Foreground-backed jobs are hidden from lists and suppress result delivery. Foreground wait races completion against a threshold, caller cancellation and (in this harness) an incoming-message signal. Completion releases the hidden job; threshold/incoming-message relinquishes updates and promotes it. Cancellation cancels the job. The waiter clears its timer/listeners in `finally`, avoiding ref'd timers holding shutdown after fast completion. Default threshold is 60 seconds and subtracts a one-second execution-timeout buffer. Cap exhaustion falls back to direct foreground execution rather than killing another job.

`backgroundJob` unsuppresses delivery and, if the job already settled, queues that result. `releaseForegroundJob` discards after actual settlement. This handles the completion-at-promotion boundary without conflating cancellation and detachment. The default running-job cap is 15; delivery retry/retention/consumed-results mechanisms are substantial separate state. Waiting snapshots may suppress asynchronous delivery. Owner IDs scope queries/cancels. The manager marks cancellation immediately while retaining promise settlement for actual reap; the distinction matters for Blackbird status vocabulary.

Interactive PTY is a separate path and takes precedence over auto-background. `tools/bash-interactive.ts` binds overlay key/resize callbacks to an existing `PtySession`; both overlay close handlers kill it. No background/return path was established for that interactive branch. Thus an excellent managed-job pattern does not by itself satisfy the operator's foreground interaction requirement.

Native PTY collection is valuable independent evidence. `crates/pi-natives/src/pty.rs` puts reader→JS output in a 64-chunk bounded queue, at most 64 KiB/read, and separates the forwarding pump from input/resize/kill/try_wait. It distinguishes a stuck slave after child exit from queued output or an in-flight slow callback. Post-cancel drain is 300 ms; POSIX cancellation reaping polls 500 ms then hands wait to a detached thread, preserving eventual reap without freezing the caller. This makes output/backpressure status part of drain correctness, not only a fixed grace constant.

Read tests: `async-job-manager.test.ts` foreground hiding/release/promotion even after settlement, owner isolation, bounded disposal and late settlement; native `pty_pump_bounds_queue_and_delivers_all_bytes` produces patterned 2 MiB and independently compares concatenated bytes and order, while checking queue capacity. Drain tests distinguish actual EOF, queued backpressure, callback latency and an open slave. The native zombie cancellation-storm test is an additional lifecycle oracle. These are stronger patterns than merely checking flags or a UI snapshot.

## Hermes: adoption preserves the child, but moving decoders is dangerous

Implementation: `quarantine/hermes-agent-2026-10-07/tools/process_registry.py` (`adopt_local`, `_reader_loop`, `_finish_reader`, detached recovery); `tools/environments/{base.py,base_output.py}`. Foreground waiter starts a drain thread. On yield it sets drain-stop, joins for up to one second, and passes the existing `Popen` plus rendered captured output to the registry. The registry seeds its rolling output and begins reading the remaining same pipe. Failed handoff restarts foreground draining. The child itself is never relaunched.

A specific source-derived defect candidate follows. The foreground reader owns an incremental UTF-8 decoder and finalizes it in `base_output._drain_stdout`'s `finally`, including on handoff stop. `adopt_local` passes rendered text, not the decoder's partial byte state; the new registry reader initializes a fresh decoder. If a character's leading bytes are read before handoff and continuation bytes afterward, the same valid character can become replacement characters. Existing reader split-character tests cover one decoder's continuous lifetime, not this boundary. A handoff join timeout also lacks an `is_alive` check before adoption; POSIX/Windows stop-aware drains normally return within polling intervals, but stream adapters or blocked collectors can leave competing consumers. These are hypotheses established by control flow, not imported dynamic reproductions. Blackbird can eliminate both by maintaining one raw-byte collector for the entire job lifetime.

The registry separately observes direct-child exit and descriptor EOF. `_finish_reader` waits/reaps after early stdout EOF rather than inventing completion. Its POSIX reader uses select/read1 and bounded idle after direct-child exit when an orphan holds the pipe; decoded text flushes incomplete tails. Recovery records PID start-time evidence where available, refuses signaling a clearly recycled PID, and distinguishes gone-without-collected-exit from actual completion. Missing start-time evidence degrades to numeric liveness; this does not give full cross-platform identity. GUI close is explicitly read-only view closure without killing the process. PTY input/close-stdin capabilities exist separately from adopting the foreground pipe.

Tests read: `tests/tools/test_process_registry.py` early stdout EOF waits for actual child, failed wait does not fabricate status, actual orphan-held pipe finishes promptly and preserves output, incremental decoding and invalid-byte handling, recycled-PID refusal, signal-ignoring child escalation and tree kill. The orphan test obtains PGID *after* parent exit for cleanup, which can fail once that PID is gone: Blackbird's fixtures should save PGID at spawn and reap/kill descendants through known ownership. Source also covers completed notification races and recovered scopes. Real OS cases are useful; they must have fixtures whose own cleanup does not leak children.

## Additional contrasts

`quarantine/opencode/packages/opencode/src/tool/shell.ts` scopes a spawned handle to the synchronous tool execution, forks output collection in the same scope, and races exit against abort and timeout. Abort/timeout kills with three-second force escalation. It spills long output to an append stream, closes the sink in a finalizer, and returns after scope exit. This inspected shell path lacks an owned background-job/reattach protocol; treating scope cancellation as merely “background” would destroy the required owner. This source supplies a useful negative comparison for Blackbird's currently synchronous command path.

`quarantine/goose/crates/goose/src/agents/platform_extensions/developer/shell.rs` also has a synchronous child-wait/timeout/cancellation path with a separate output collector. Its login-shell PATH resolver starts a new session specifically to avoid interactive shell job-control startup stealing Goose's terminal foreground. This concrete failure mechanism reinforces that operator terminal ownership cannot be assumed from process-group isolation. These narrower reads do not claim a complete survey of all OpenCode/Goose terminal subsystems.

## Consequences for the owned design and direct oracles

1. **One launch, one permanent owner.** Create the job before spawn becomes externally visible. Background changes waiter/attachment only; foreground binds to the same job. A child fixture emits PID plus a nonce to an external file and monotonically increments an external counter. Alternate attach/detach repeatedly; require identical identity, continuous counter and exactly one launch record. Returned strings alone cannot establish this.
2. **One permanent raw collector.** Keep stream offsets and incremental decoding independent of observers; append originals once. Each consumer uses its own cursor or explicitly declared destructive polling semantics. A fixture emits a known binary pattern in adversarial chunking, with UTF-8 characters split precisely across detach/attach, stderr interleaving and terminal control bytes. Compare retained bytes to generated bytes exactly; separately test rendered meaning and sanitization. A model response cap must not cap originals silently.
3. **Exit, EOF, drain, cancellation and loss are distinct evidence.** Drive children that close output but continue alive, exit while descendants hold writers, emit a large tail at exit, ignore TERM and receive KILL, and die during attach/poll. Establish status from child wait/signal outcomes and output sealing from collector observations. Do not infer completion from empty read/current file end/heartbeat expiry. A bounded drain must report incomplete capture if that is its policy.
4. **Stable identity and serialized mutations.** A job ID is not a PID. Use generation/session identity; queued operations must not target a replacement. A deterministic event model can enumerate attach/detach/write/exit/drain/shutdown orders. Fake process adapters should record all launches, signals, writes and closes so expected effects derive from a small independent model. Real child tests attack OS lifecycle separately.
5. **Detachment is not cancellation.** Unsubscribing, closing a view, returning a bounded wait or abandoning a tool response must not release the last process owner. Kill is an explicit operation; an accepted kill request is distinct from observed termination and reap. Block a renderer deliberately, then require input, stop and status to remain live, output bounded by the specified queue/spool policy, and eventual child reaping.
6. **Capacity policy belongs in behavior.** Do not copy silent live-job LRU kill. At capacity, specify refuse/spill/operator eviction and test that existing jobs remain untouched. Separate limits for running jobs, retained metadata, resident output and disk originals; describe actual disk/I/O failure and truncation outcomes.
7. **Foreground must have an end-to-end operator meaning.** Drive Blackbird under a test PTY, launch a child that reads and echoes input, background it, work in the composer, reselect it, send input and resize, then detach again. Assert input reaches only the selected child, composer text is preserved, child PID stays constant and terminal mode/cursor restores after exit. Include raw-mode, multiline, Ctrl-C/Ctrl-D, invalid selection and attachment-exit races. Pipe-only waiting is valuable but does not qualify interactive foreground return.
8. **Shutdown/restart scope must be explicit.** If session jobs terminate with Blackbird, verify all owned nonescaped descendants actually exit/reap and reopened metadata reports loss/known result honestly. If jobs survive restart, a detached worker/daemon must own wait/I/O before main process disappears; persisted PID alone cannot reconstruct a lost pipe or child wait handle. Kill/restart at every launch/registration/drain boundary, including capture-write failure. Never relaunch an uncertain command automatically.

Static review should trace ownership and cleanup through every return/throw/cancellation path, verify no await drops the last owner before registration, ensure a foreground attachment cannot own destructive cleanup accidentally, and account for bytes/copies/queue bounds. Dynamic testing should use the direct OS, byte and terminal oracles above. Model/event schedules and sanitizers attack different faults; neither is a substitute for the process-identity and byte-conservation checks. Mutation campaigns, if selected, run on the fleet, not this laptop. No design approval or product qualification is claimed by this research report.
