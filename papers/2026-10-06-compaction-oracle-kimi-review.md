## Remaining consequential holes (with direct red cases)

**F1 — Malformed appended suffix never tested against settlement.** The plan (MANAGED_COMPACTION_SUBPLAN.md:182–184) states "appended malformed protocol intentionally rejects settlement," and the mechanism exists (`src/context.cpp:466–509`, suffix merged before `protocol_complete(next)`), but no test ever appends a protocol-breaking entry between stage and `finish_workflow(true)`. A regression that ran `protocol_complete` only over `basis`, or skipped it on the settlement path, would pass the entire suite. *Red case*: begin workflow, stage archive, `context->append({function_call with no result}, ...)` or a dangling `function_call_output`, then require `finish_workflow(true)` rejected with `invalid-tool-protocol` and view unchanged.

**F2 — Only one post-stage tool round is exercised at engine level.** The "settlement at END, not at intermediate provider calls" oracle covers exactly one intermediate request whose response appends *no* further items (ManagedToolProvider emits a call only on `calls == 1`; coding_test.cpp:20–26). The suffix-preservation loop (`src/context.cpp:470–472`) is never tested against multiple appended batches with interleaved tool groups after the proposing exchange (e.g., a second function_call/result pair plus reasoning after `context_manage`). *Red case*: provider that issues a second tool call after the `context_manage` result; assert published view preserves both suffix exchanges in exact order and that both intermediate requests carried the pre-settlement bytes.

**F3 — `inspect` offset beyond `total_bytes` silently clamps** (`src/context.cpp:573`: `offset = std::min(index_field(...), raw.size())`). The campaign's "invalid offset" cases cover -1 and nonnumeric only, and only against `kind:"index"`; beyond-EOF offset and any bounds tests for `history`/whole-array `originals` kinds are absent. Either define clamping as contract (then test it explicitly) or reject with `invalid_range` (then red case: offset = total+1 must throw). Consequence today: a paging repair client gets a duplicate EOF page indistinguishable from legitimate EOF.

**F4 — Rejection *auditing* is never asserted.** Contract requires candidate + acceptance/rejection + revisions recorded for every transformation; `reject_managed` does record packets (src/context.cpp:322–340), but every test only asserts the returned outcome and unchanged view. A regression dropping the rejected candidate from history would pass. *Red case*: after a stale/invalid rejection, page `kind:"history"` and require the packet with `accepted:false`, original candidate bytes, and reason.

**F5 — Randomized 160-step model contains no protocol groups.** All seeded/appended items in the loop are role/reasoning entries; the persistent generic reorder (action 8) and sparse restore + reopen can therefore never interact with call/result grouping constraints in the model. Group repair is covered only in the fixed parallel section (compaction_campaign_test.cpp:395–432), which is never followed by a reopen. *Red case*: add completed call/result pairs to the seeded model domain so reorder/restore/reopen transitions randomly cross group boundaries; add one reopen after the corrupted-order repair at line 420.

**F6 — Scale oracle does not verify repairability at scale.** Originals are asserted immutable after replay, but no bounded paged retrieval of a summarized-away needle (e.g., turn-17's 8 KiB output) is performed on the reopened scale store; paged roundtrip is only exercised in the small fixture. Cheap addition: `inspect` one 8 KiB needle entry with 4096-byte pages after reopen and byte-compare against the retained `scale_originals`.

## Minor observations (no action required for correctness)

- compaction_campaign_test.cpp:185 (`clear.object()[1].second`) relies on `view()` key order; brittle but currently stable.
- `CodingEngine::turn` displays a settlement-conflict outcome as informational text rather than an error (src/coding.cpp:878–880); audited, so acceptable, but an operator could miss it.
- Stale-supplied-base rejection is tested only via the store API; the `context_manage` path shares `manage()`, so risk is low, but one engine-level stale-base negative case would close the surface symmetrically with the omitted-base positive case.
