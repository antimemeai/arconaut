# Teams and true multiplayer: independent Arconauts sharing a build

Research snapshot: 2026-10-06. This is a discussion artifact, not a release gate or dependency proposal. References were downloaded and source/tests read; none were executed, authenticated, or adopted. `manifest.json` records exact revisions, unchanged archives, hashes, restoration instructions, and saved official documentation. A test described below is an inspected oracle, not a claimed passing result.

The target is **n independently running Arconauts collaborating on a project/build over a network**, retaining separate local runtimes, contexts, and audits. Two Arconauts and two humans are the initial concrete exercise. Human–human, human–agent, and agent–agent communication all matter. Either Arconaut may disconnect or refit while peers continue. This is broader than a leader spawning workers, and broader than several devices viewing one session.

## Current Claude Code: teams were changed, not abolished

The official [teams page](https://code.claude.com/docs/en/agent-teams) remains separate; its saved Markdown URL did not redirect. Teams are experimental, disabled by default, interactive-only, and enabled by `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`. A named Agent invocation launches a teammate under that mode, with exceptions for fork/isolation. A session has one implicit team, a fixed lead, and no nested teams. Teammates receive project context and their spawning prompt rather than the lead's conversation history. Team configuration and JSON inboxes live locally; inbox-write success establishes sending, not model consumption. Task claiming uses file locking. Cooperative shutdown waits for current work, and `/resume` or `/rewind` does not restore in-process teammates. These are useful worker orchestration mechanisms; they do not establish independent network peers or multiple human operators.

The precise [official changelog at the acquired revision](https://github.com/anthropics/claude-code/blob/8e60c4cac989c0e0cc6d2c49407a5c67f5a4a8e6/CHANGELOG.md#21178) says version 2.1.178 removed `TeamCreate` and `TeamDelete`, made the team implicit, and retained-but-ignored `team_name`. Thus “teams merged into subagents and disappeared” is an incorrect interpretation. The public repository contains changelog/documentation, not the implementation needed to independently verify the CLI's internal delivery and locking behavior.

Current [subagent documentation](https://code.claude.com/docs/en/sub-agents) separately describes background workers and named messaging. `SendMessage` can resume a completed or stopped worker in the background with the same identifier and conversation history after its prior run exits. An operator-cancelled worker does not automatically resume through a model message. Configurable nesting and concurrency limits exist; non-forked workers do not inherit parent history, whereas forks do. Tool availability differs across foreground/background and team modes, so reusing an agent definition does not promise equivalent execution semantics. This is a continuity and cancellation reference, not a reason to import fixed topology or limits into Arco.

The [cross-session messaging documentation](https://code.claude.com/docs/en/cross-session-messaging) is closer to independent colleagues. Local transport uses Unix sockets or Windows named pipes; remote transport uses Remote Control/cloud relay in the account's session scope. Busy sessions read between tool calls; idle sessions may start a turn. Messages are plain text, not shared context or automatic file attachment. Delivery can be held or refused; outbound sending does not establish consumption. Remote offline sessions can queue until reconnection. A sender without a return address cannot assume bidirectional replies. There are environment boundaries and a limited local idle notification mechanism. This documents session messaging, not multi-human project membership, coherent shared builds, or durable peer context inclusion.

[Remote Control](https://code.claude.com/docs/en/remote-control) keeps work on the local computer and exposes an existing session through terminal/browser/phone interfaces. It requires the local process/computer to remain available. Server mode can use shared directories or worktrees. Multiple views of an account's session are therefore not evidence of multiple independent Arconauts or independent human identities.

## Three concrete reference mechanisms

### ICE: live edits need a separate publication boundary

Pin: `opencolin/ice@5beb4bcf9230fd80bc4e68060d79fc90fa9b5f74`.

In [room-doc.ts](https://github.com/opencolin/ice/blob/5beb4bcf9230fd80bc4e68060d79fc90fa9b5f74/apps/server/src/room-doc.ts), `getRoomDoc` shares a live YDoc per room, including concurrent-open coalescing. Agents access that actual document instead of an unrelated file copy. [realtime.ts](https://github.com/opencolin/ice/blob/5beb4bcf9230fd80bc4e68060d79fc90fa9b5f74/apps/server/src/realtime.ts) restores persisted room data and seeds Git only when the document's file map is empty. Its comments explicitly defer three-way merging for external pushes into an already-open room.

[convergence.ts](https://github.com/opencolin/ice/blob/5beb4bcf9230fd80bc4e68060d79fc90fa9b5f74/apps/server/src/convergence/convergence.ts) snapshots files before asynchronous materialization, serializes `flushAndCommit` per room, and returns a Git commit identity. The desired file set is authoritative, including deletions. [lock.ts](https://github.com/opencolin/ice/blob/5beb4bcf9230fd80bc4e68060d79fc90fa9b5f74/apps/server/src/convergence/lock.ts) implements a process-local FIFO mutex, not distributed publication fencing. Optional Redis synchronization does not itself prove that several servers serialize Git publication.

The decisive inspected oracle is [convergence.test.ts](https://github.com/opencolin/ice/blob/5beb4bcf9230fd80bc4e68060d79fc90fa9b5f74/apps/server/src/convergence/convergence.test.ts). It checks exact UTF-8 contents, deletions, round trips, authorship, and a linear parent chain under parallel flushes. For two distinct snapshots, its final-tree expectation is **entire snapshot A or entire snapshot B**, depending on order. It does not establish preservation of both proposals or semantic merge correctness. A linear history can still discard another writer's unique files.

[agent/host.ts](https://github.com/opencolin/ice/blob/5beb4bcf9230fd80bc4e68060d79fc90fa9b5f74/apps/server/src/agent/host.ts) has per-room/per-agent backends and records human prompts before dispatch. [host.test.ts](https://github.com/opencolin/ice/blob/5beb4bcf9230fd80bc4e68060d79fc90fa9b5f74/apps/server/src/agent/host.test.ts) checks prompt/reply records, edits, idempotent starts, and terminal-runner injection; commands without that runner are no-ops. These are local/mock integration checks, not demonstrated network collaboration by two independent provider-backed runtimes.

**Transfer:** distinguish interactive document convergence from an immutable published source tree. A compiler should consume the latter. CRDT text convergence neither proves coherent compiler inputs nor resolves semantic conflicts. ICE offers a strong human/agent editing reference but not the entire independent-peer target.

### Commonly: rooms can connect native runtimes without merging their sessions

Pin: `Team-Commonly/commonly@5bd4f1af4a6adaf4e9c2aeee2a23b21ba50e701f`.

[messageController.ts](https://github.com/Team-Commonly/commonly/blob/5bd4f1af4a6adaf4e9c2aeee2a23b21ba50e701f/backend/controllers/messageController.ts) persists messages, routes them to agents, and emits room messages to human viewers. Socket broadcast failure can be logged while the persisted message is still returned successfully: persistent acceptance and live display are distinct. [agentMentionService.ts](https://github.com/Team-Commonly/commonly/blob/5bd4f1af4a6adaf4e9c2aeee2a23b21ba50e701f/backend/services/agentMentionService.ts) routes explicit mentions/replies and opt-in wake behavior, including bot-to-bot routing with self-exclusion and loop dampening. Those policies are choices, not universal peer behavior.

[agentEventService.ts](https://github.com/Team-Commonly/commonly/blob/5bd4f1af4a6adaf4e9c2aeee2a23b21ba50e701f/backend/services/agentEventService.ts) atomically claims a pending event, increments delivery attempts, and assigns a delivery nonce. Acknowledgment can match that nonce, separating an old worker's delayed acknowledgment from a newer delivery. However, the migration path accepts absent nonces unless required for that consumer. This does not justify an unconditional exactly-once claim. [agentsRuntime.ts](https://github.com/Team-Commonly/commonly/blob/5bd4f1af4a6adaf4e9c2aeee2a23b21ba50e701f/backend/routes/agentsRuntime.ts) exposes scoped event retrieval and acknowledgments for agent/instance identities.

The actual [Codex adapter](https://github.com/Team-Commonly/commonly/blob/5bd4f1af4a6adaf4e9c2aeee2a23b21ba50e701f/cli/src/lib/adapters/codex.js) invokes `codex exec resume` with the driver's native session identifier and configured working directory, preserving native history while exchanging room messages. Its timeout sends SIGTERM and waits for close; the inspected path does not establish guaranteed kill escalation or quiescence.

Inspected tests include `backend/__tests__/unit/services/agentMentionService.threadingIsNotAddressing.test.js`: thread membership alone must not enqueue a wake; replying to the bot does. This is a useful paired positive/negative oracle. `backend/__tests__/service/two-driver-memory-cross-check.test.js` checks isolation by agent/instance across two installed driver identities against test Mongo. It does not run two real remote models editing/building the same project.

**Transfer:** preserve each runtime's context/session while exchanging explicitly addressed room events. Distinguish thread grouping, recipient routing, delivery attempt, acknowledgment, and actual model inclusion. No coherent shared build identity was established in the inspected paths. Commonly's hosted governance/provisioning is outside Arco's role as customer of external computation.

### Agent Room: durable conversation and bounded presence are independent of inference

Pin: `agent-room-alkl/agent-room@080b13d2bf927a1ee3e66981dece0d2eee698d37`.

[RoomPersistence](https://github.com/agent-room-alkl/agent-room/blob/080b13d2bf927a1ee3e66981dece0d2eee698d37/packages/room-persistence/src/types.ts) separates room records, messages, CAS updates, receipts, and lease events. In [postgres.ts](https://github.com/agent-room-alkl/agent-room/blob/080b13d2bf927a1ee3e66981dece0d2eee698d37/packages/room-persistence/src/postgres.ts), `appendMessage` locks the room row, allocates a sequence, and handles repeated IDs idempotently only when payloads agree; reusing an ID with different content errors. Replay is ordered by room sequence. This is durable acceptance, not proof a model read or acted on a message.

[postgres.integration.test.ts](https://github.com/agent-room-alkl/agent-room/blob/080b13d2bf927a1ee3e66981dece0d2eee698d37/packages/room-persistence/test/postgres.integration.test.ts) closes/reopens the record server, advances a fake clock 25 hours, and checks messages, taskboard, minutes, receipts, and lease records survive. It also checks repeated receipts do not duplicate and conflicting IDs are rejected. This is a concrete restart oracle in source. The separate hosted Redis client uses capped/TTL storage, so its retention must not be conflated with the durable Postgres path.

[presence.ts](https://github.com/agent-room-alkl/agent-room/blob/080b13d2bf927a1ee3e66981dece0d2eee698d37/packages/shared/src/presence.ts) renews a bounded lease while listening and expires it on exit; write failures do not break the listener. [presence.test.ts](https://github.com/agent-room-alkl/agent-room/blob/080b13d2bf927a1ee3e66981dece0d2eee698d37/packages/shared/src/presence.test.ts) checks renewal, stop, expiry, and failure handling. This is an activity hint, not proof of death during a network partition.

The MCP listener carries a cursor and supports long polling. Model instructions that encourage indefinite listen-tool calls are not a desirable station implementation for Arco: an ordinary network listener can queue events without spending inference. No shared source/build machinery was established in the inspected paths.

**Transfer:** durable sequence replay, idempotent IDs with payload collision checks, bounded presence, and receipts that name their actual stage. Existing corpus study `papers/capabilities/studies/collaboration-orchestration.md` was reused first; its Agentchat findings already show why transport success, truncated history, and missing model-visible IDs are insufficient. These acquisitions add stronger source oracles rather than another unexamined agent zoo.

## Arco options, without selecting a server or filesystem topology

The following are design inferences for discussion, not capabilities claimed for the references.

1. **Independent contexts, explicit collaboration.** Name the human, Arconaut session, runtime incarnation, room, and context revision separately. Shared room membership does not merge histories. Locally audit original received events; later record which revision/request actually included them. Distinguish accepted, queued, included, acted-on, and failed. A peer's recommendation and a human's instruction retain provenance without introducing command approval ceremonies.
2. **Source and build identity.** A proposal names its immutable source base and patch/tree; publication compares the expected base and reports conflicts rather than silently replacing another proposal. A build artifact names the source tree, relevant toolchain/configuration inputs, and result content identity. “Latest build” is a convenience pointer, not evidence of inputs. External build services and databases remain customers' resources, not Arco-governed processes.
3. **Network events and reconnection.** Use stable message IDs, sender incarnation, explicit recipients, optional reply edges, and a replay position appropriate to the chosen transport. Retried identical events deduplicate; conflicting reuse is visible. Missing retained history produces a gap event. A presence timeout is uncertainty, not permission to steal an unfenced publication right. Human–human traffic must remain useful with every model idle.
4. **Refit independence.** A refitting Arconaut quiesces its own provider requests and active programs and pauses its standing clients. It does not pause peers or external shared computation. A departure/refit notice is advisory. On return it keeps its own session and context, replays missing events, and evaluates stale source proposals against current publication state. Unknown outcomes of earlier side effects are reconciled, not blindly repeated.
5. **Operator steering.** Network arrival does not automatically interrupt generation or tools. Default admission waits for the affected turn/workflow boundary; explicit interrupt-and-apply-now follows the operator's existing semantics. Addressing and activation are separate controls. Cross-provider topology and configurable limits remain possible rather than inheriting one vendor's lead hierarchy or numeric caps.

Three viable workspace arrangements remain open. Separate checkouts exchanging patches/trees make independent continuity and conflict detection simplest. A shared remote filesystem can be convenient but needs explicit writer coordination and immutable build snapshots. A live collaborative document needs a projection/publication step and substantially more machinery; its convergent text still needs semantic review. Room/event transport is orthogonal to these choices. None requires centralizing all Arconaut contexts.

## Small direct exercise before a large campaign

Use two actual Arconaut processes on two hosts and two distinguishable human clients, then extend the same identities/protocol to a third peer. No special two-peer limit. Provider diversity is a useful separate treatment when credentials/capabilities permit, not a prerequisite for basic networking.

- Demonstrate all three communication classes: humans exchange a project constraint; a human targets one Arconaut while it is active; one Arconaut sends the other a build failure with immutable input/artifact references. Assert exact sender/recipient and eventual actual-request inclusion, not merely mailbox arrival. Human conversation works with models idle.
- Start from a known source tree with an independently specified behavioral oracle. Produce overlapping proposals from the same base and show explicit conflict/no silent overwrite; separately exercise disjoint composition. Compile a named immutable tree and match the expected behavior and input identity. A mutable directory or linear commit graph alone is insufficient.
- Inject duplicate messages, reordering, a reconnect, and a retention gap. Assert deduplication/collision behavior, replay position, and visible uncertainty. Do not call local mocks a two-host demonstration.
- Disconnect/refit A while B continues communicating and building. Assert B's work completes, A retains its own session/context identity, missing events become available without context merge, and stale publication is detected. Check no active request/program remains in A at refit and that uncertain side effects are not replayed.

Record provider requests/tokens/cost, both humans' attention/interventions, wall-clock latency, source revisions, transport gaps, conflict outcomes, and actual request inclusion separately. Compare the same useful task against today's manual sharing, with equal instrumentation in both arms. The immediate outcome is a working, legible collaboration path; a room transcript, more simultaneous agents, or a smoother animation is not evidence of faster or more correct development.
