## 0. Core Principle: Bicycles for Megan's Mind

**Megan should never do mechanical work that a traditional program can do better.** She manipulates meaning; the environment handles representation. Traditional programs (neovim, brush, ast-grep, tree-sitter) are the bicycles for her mind — they amplify her reasoning without requiring her to do friction-heavy labor.

### What This Means in Practice

| Instead of Megan... | The bicycle does it |
|---|---|
| Parsing raw terminal output, scrolling history, counting lines | **Structured shell log** — semantically marked commands/results, cursor remembers her place |
| Matching exact strings, handling whitespace drift, stale context | **AST-based editing** — she says "the function named `refresh_token`", neovim resolves it structurally |
| Tracking line numbers that shift after every edit | **Extmarks** — semantic labels that survive all edits automatically |
| Opening files manually, waiting for loads, losing context | **Predictive buffer manager** — files warm in neovim before she asks |
| Searching for symbol definitions across files | **Tree-sitter queries** — she asks "where is `OAuthFlow` defined?" and gets the exact node |
| Reading entire files to find relevant context | **Working set + AST previews** — she gets just the relevant functions, not whole files |
| Remembering what she ran 20 turns ago | **ShellHistory vector DB** — she queries "what was the exit code of that cargo test?" |

**Megan's cognition = pure reasoning.** The environment = invisible, frictionless, anticipatory.

## 3. Neovim Headless as Native Code Runtime

**Decision:** No optional backend. `read`, `write`, `edit` are DELETED from base tools.
Replaced by `ReadNV`, `WriteNV`, `EditNV` — neovim-native variants.

### Architecture
- arconaut-agent spawns `nvim --embed` as a child process.
- Direct MessagePack RPC via `nvim-rs` crate — NO brush intermediation.
- Lua bridge: custom `arconaut.lua` module loaded into neovim.
- Brush handles shell commands (`cargo test`, `git log`). Neovim handles all file manipulation.

### Key Capabilities
- Live tree-sitter CSTs for every buffer.
- Extmarks for stable semantic references across edits.
- Undo/redo history (transactional experimentation).
- Multi-buffer editing.
- Structured queries instead of string matching.

### Tool Schema (Preliminary)

**ReadNV:**
```json
{
  "path": "src/auth.rs",
  "ast": true,
  "range": [10, 50]
}
```

**EditNV:**
```json
{
  "path": "src/auth.rs",
  "selector": "(function_item name: (identifier) @f (#eq? @f \"old_name\"))",
  "replacement": "fn new_name() {}",
  "mode": "query"
}
```

### Buffer Manager — Predictive Working Set

LRU cache with Markov transition prefetching.
- **L1: Graph Prefetch** — parse imports/dependencies, preload 1-2 hops.
- **L2: Markov Transition** — track X→Y frequencies, prefetch top-k successors.
- **L3: Working Set Clock** — protect recently-touched files from eviction.

**Key scenario:** Agent repeatedly auth.rs → oauth.rs → token.rs → auth.rs.
When she opens auth.rs, evict LRU buffer Q and preload oauth.rs while she's in auth.rs.

**Literature to pull:**
- Griffioen & Appleton (1994) — predictive file system, Markov transitions.
- Joseph & Grunwald (1997) — Markov prefetchers.
- Esfahbod (2006) — Preload daemon, continuous-time Markov chains.
- Denning (1968) + Carr & Hennessy (1981) — Working set + WSClock.
- Megiddo & Modha (2003) — ARC replacement.
- Jiang & Zhang (2002) — LIRS.

## 4. TUI Right-Side Terminal — AGENT'S Terminal

**CRITICAL ARCHITECTURAL CLARIFICATION:**

The right-side terminal tile in the TUI is **NOT** the operator's terminal.
It is **arconaut's** persistent terminal — her "1 model chatroom with terminal outputs."

### What This Means
- The operator CAN input commands into it.
- It is ABSOLUTELY arconaut's alongside everything we've been discussing.
- This is where she would `ssh` into a runpod pod and just run that shit.
- `brush` + `neovim` handle most things, but the persistent terminal covers what nothing else can:
  - SSH sessions to remote hosts
  - Long-running interactive processes
  - Docker exec, kubectl, etc.
  - Anything requiring a real TTY/pseudo-terminal

### Architecture
```
┌─────────────────────────────────────────────┐
│  arconaut TUI                               │
│  ┌──────────────────┐  ┌──────────────────┐ │
│  │  Chat panel      │  │  Terminal panel  │ │
│  │  (agent+human)   │  │  (AGENT'S SHELL) │ │
│  │                  │  │  brush-core + TTY│ │
│  │  Agent turn loop │  │  OSC 633 marked  │ │
│  │  Human can type  │  │  Human CAN type  │ │
│  └──────────────────┘  └──────────────────┘ │
└─────────────────────────────────────────────┘
         ↓                              ↓
┌──────────────────┐          ┌──────────────────┐
│  Neovim headless │          │  Brush-core shell│
│  (code runtime)  │          │  (command exec)  │
│  --embed, no TTY │          │  -i, real TTY    │
└──────────────────┘          └──────────────────┘
```

### Distinction
| | Neovim Headless | Brush Terminal |
|---|---|---|
| **Purpose** | Code editing, AST queries, structured manipulation | Command execution, SSH, interactive processes |
| **TTY** | No (piped stdin/stdout) | Yes (pseudo-terminal) |
| **Interaction** | RPC calls from agent | Shell commands, human can type |
| **Persistence** | Buffers stay open across turns | Shell session stays alive across turns |
| **OSC 633** | Not applicable | Yes — command boundaries, exit codes, Cwd |
| **Examples** | `EditNV`, `QueryAST` | `ssh runpod`, `docker exec -it`, `htop` |

### RTerm Tools — Structured Shell Log (CRITICAL)

**RTermRead** and **RTermWrite** are NOT raw terminal I/O tools. They operate on a **structured shell log** that arconaut maintains.

#### Architecture

```
┌─────────────────────────────────────────────────────────────┐
│  Brush-core shell (RTerm)                                   │
│  ├─ Runs commands, captures output                         │
│  ├─ OSC 633 marks command boundaries                      │
│  └─ Output stream → arconaut structuring layer            │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  Arconaut Structuring Layer                                 │
│  ├─ Parses OSC 633 sequences                               │
│  ├─ Formats into structured shell log                      │
│  ├─ Appends to nvim buffer (always open)                   │
│  └─ Audit log gets full fidelity copy                      │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  Structured Shell Log (nvim buffer, persistent file)       │
│  ├─ Hyper-structured convention (neovim-native format)     │
│  ├─ Cursor remembers Megan's reading position              │
│  ├─ Queryable by structure (not just text)                 │
│  └─ Always kept in buffer once opened in session           │
└─────────────────────────────────────────────────────────────┘
                            ↑↓
┌─────────────────────────────────────────────────────────────┐
│  Megan (Soul)                                               │
│  ├─ RTermRead → reads from structured log (not raw tty)    │
│  ├─ RTermWrite → writes command to structured log          │
│  │   └─ Arconaut intercepts → submits to shell             │
│  │   └─ Only logs if command ACTUALLY LAUNCHES             │
│  └─ Shorthand codes (^C, etc.) → control signals           │
└─────────────────────────────────────────────────────────────┘
```

#### RTermRead

- **NOT** "read raw terminal output."
- Opens the **structured shell log file** (always in nvim buffer).
- Returns content from Megan's **last read position** (cursor remembered automatically).
- The log is structured using a "neovim hyper structured convention" — designed for structural querying and editing.
- Arconaut maintains this log; Megan never sees raw tty escape sequences.

#### RTermWrite

- Megan writes a command entry in the **same structured format** as the log.
- Arconaut **intercepts** the write:
  1. Extracts the command from the structured entry.
  2. Submits it to the brush-core shell.
  3. **Only writes to the log if the command actually launches.**
  4. Shell output streams back via OSC 633.
  5. Arconaut formats output and appends to the structured log.
- **Shorthand codes:** `^C` (ctrl-c), `^D` (ctrl-d), etc. — Arconaut translates these to actual control signals sent to the shell process, not literal text.

#### Structured Log Format (Preliminary)

Hyper-structured convention designed for neovim parsing:

```markdown
# Shell Session Log — arconaut

## [seq:42] [2026-06-07T12:34:56Z] cargo test
- **cwd:** /Users/patrickbeam/projects/arconaut
- **duration:** 45.2s
- **exit:** 0

```output
running 109 tests
test auth::tests::token_refresh ... ok
test result: ok. 109 passed; 0 failed
```

---

## [seq:43] [2026-06-07T12:36:12Z] ssh runpod
- **cwd:** /Users/patrickbeam/projects/arconaut
- **duration:** —
- **exit:** —
- **status:** running

```output
ubuntu@runpod:~$ █
```
```

Or potentially a custom tree-sitter grammar for even richer structural querying.

#### Railroad Traffic Signaling

Visual state indicators on the terminal panel surface (ratatui overlay + OSC 633):

| Signal | Meaning |
|--------|---------|
| 🟢 **GREEN** | Terminal idle — human free to type, agent not using |
| 🟡 **YELLOW** | Agent about to send command — human wrap up |
| 🔴 **RED** | Agent has control — command executing, do not type |
| ⚡ **FLASH** | Interrupt signal sent (^C, ^D) — breaking current process |

Push minor interrupt prompts: when agent sends ^C, surface flashes and shows "▶ agent: interrupted" briefly.

## 5. Structural Editing Research

Research request submitted: `req-20260607-192342-449829000-15111`
- CodeStruct (Amazon, ACL 2026)
- ast-grep, comby, gritql for LLM agents
- Editor-as-API paradigms (Acme 9P, neovim RPC)
- Agent file editing robustness (failure modes)

### Key Findings Summary
- Current agents converge on `old_string`/`new_string` — 50% failure rates.
- CodeStruct: AST-based editing reduces errors 76-88%, tokens 12-38%.
- ast-grep (Rust): Tree-sitter query rewriting, JSON output, MCP server exists.
- comby: Syntax templates with holes `:[var]`, 40+ languages.
- Aider: 13 edit formats, 9-step fuzzy matching chain. `editblock` (SEARCH/REPLACE) most robust.
- Neovim RPC: `nvim_buf_set_text` for precise range edits, tree-sitter built in.

## 8. Vectored Tool — Embedding Query System (Decided, Later Tranche)

**Status:** Decided. System-level ambient intelligence, NOT a Megan-facing tool. Design deferred to later tranche when embedding infrastructure matures.

Megan does NOT interact with Vectored Tool directly. Arconaut (the Soul/system layer) makes these calls automatically, injecting synthesized context and framing that Megan doesn't need to burn tokens on.

### Three Verbs

| Verb | Corpus | What It Queries | Use Case |
|------|--------|-----------------|----------|
| **`Trajectory`** | Embedded audit log | arconaut's own session history, tool calls, errors, resolutions | "Have I seen this error pattern before? How did I fix it last time?" |
| **`Assemblage`** | Embedded repository | The codebase arconaut is currently working on | "Where is the relevant code for this feature? What functions touch this data?" |
| **`Rhizome`** | Library embeddings | The entire neurotic_library collection (~5,300 papers across topics) | "What does the research literature say about this problem domain?" |

### Trigger Heuristics (Soul-Level)

The Soul detects when Megan is flailing and fires Vectored Tool automatically:

| Heuristic | Detection | Action |
|-----------|-----------|--------|
| **Flailing** | Repeated failed tool calls (same error >3×), tool loops, churn detected | Fire `Trajectory` first → if no hit, fire `Assemblage` |
| **Debug Struggle** | Test failures persisting across >5 turns, no progress on fix | Fire `Assemblage` → if no hit, fire `Rhizome` |
| **Unknown Domain** | Encountering concepts not in working set, unfamiliar patterns | Fire `Rhizome` directly |
| **Context Drift** | Agent seems lost, going in circles, meandering tool calls | Fire `Trajectory` ("what was I trying to do?") + `Assemblage` |
| **Long Pause** | No useful tool calls for N turns, just asking clarifying questions | Suggest `Neurotic Seek` if Vectored returns nothing |

### Decision Logic

```
Soul detects heuristic trigger
    ↓
Construct contextual query (arconaut injects framing, recent errors, current goal)
    ↓
Fire Vectored Tool (Trajectory → Assemblage → Rhizome, in order)
    ↓
If useful results:
    → Synthesize into concise system message
    → Inject into Megan's context (NOT as raw embedding results)
    → Megan sees: "[Context] You've encountered this pattern before in session X. The fix was Y."

If nothing useful:
    → Trigger Neurotic Seek (research request to librarian)
    → Continue without injecting noise
```

### Key Design Principle

**Megan never sees raw embedding queries or vector similarity scores.** She receives:
- Synthesized insights ("You've fixed this unwrap panic before in `auth.rs`")
- Relevant code snippets from Assemblage
- Paper excerpts from Rhizome (if highly relevant)
- Or nothing — if nothing is useful, no tokens are burned on noise

Arconaut handles all the NL→query translation, context injection, and result synthesis. Megan stays in pure reasoning mode.

### Future `nl` Integration

This will come from a future version of the `nl` binary (natural language interface) that arconaut uses internally. The `nl` command translates the Soul's heuristic-triggered intent into the appropriate embedding query.

**Deferred Work:**
- Requires embedding infrastructure for audit log, repository, and library
- Requires `nl` binary upgrade to support programmatic (not just interactive) queries
- Soul heuristic detection system needs calibration
- Decision logic for "nothing useful" threshold needs tuning

## 10. Beat Tool — "Take a Beat" (Decided)

**Purpose:** A reorientation tool. When Megan loses her way, after compaction, or when the Soul detects drift, Beat provides a succinct, high-information-density state readout. Like an actor taking a beat — pause, breathe, reorient.

### Two Verbs

| Form | Trigger | What It Does |
|------|---------|--------------|
| **`Beat`** (no verb) | **Auto-injected every turn loop prompt.** Also callable manually by Megan or operator via `/beat` | Returns current pilot variables in a dense, scannable format |
| **`Beat Taken`** | Soul auto-triggers (post-compaction, flailing detection), or operator uses `/beat taken` | Injects a structured reorientation prompt into Megan's context, summarizing operating conditions |

### Pilot Variables (State Arconaut Maintains)

Variables Beat reports (subset, extensible):

```
base_dir:          /Users/patrickbeam/projects/arconaut
work_dir:          /Users/patrickbeam/projects/arconaut/crates/arconaut-agent
session_elapsed:   2h 17m
active_plan:       docs/phase5_7-subplan.md
active_phase:      "Design neovim RPC wrapper"
last_tool:         EditNV
last_file:         crates/arconaut-agent/src/soul.rs
compactions:       3
context_used:      147K / 200K tokens
working_set:       [soul.rs, persistent_shell.rs, tools.rs]
uncommitted_changes: 12 files
last_test_run:     109 passed, 0 failed (14m ago)
rterm_status:      idle (last: cargo test, exit 0)
```

### Trigger Conditions

| Trigger | Condition | Action |
|---------|-----------|--------|
| **Every turn** | Loop prompt construction | `Beat` (no verb) auto-injected as part of default context |
| **Post-compaction** | CompactionEngine fires | Auto-inject `Beat Taken` into next turn |
| **Flailing heuristic** | Same error pattern >3×, churn detected, no progress >5 turns | Soul fires `Beat Taken` with diagnostic context |
| **Operator** | `/beat` or `/beat taken` slash command | Immediate reorientation |
| **Megan** | Calls `Beat` explicitly | Readout of pilot variables |

### Design Principle

Beat is **not** a dump of raw state. It is **curated, dense, scannable**. The format is designed for LLM consumption — bullet points, key-value pairs, no prose. Megan should be able to glance at it and know:
- Where she is (directory, phase)
- How long she's been at it (session elapsed)
- What she was last doing (last tool, last file)
- Whether she's off track (context usage, uncommitted changes)

## 11. Soul vs. Arconaut — Separation of Concerns

**Critical architectural boundary:**

| **Soul (The Pilot)** | **Arconaut Logic (The Physical Plant)** |
|---|---|
| Turn execution — the LLM reasoning loop | Injector management — what goes into context |
| Tool calling decisions | Prompt injection — Beat, Vectored results, etc. |
| Tempo management | Runtime orchestration — neovim, brush, buffer manager |
| Response generation | Ambient tool orchestration — Vectored, Neurotic auto-fire |
| Checkpoint decisions | Heuristic detection — flailing, drift, struggle |
| Narration verbosity | Off-pulse support — assistant model, hooks, audit |
| Mode transitions | Operator interface — slash commands, railroad signals |

**Soul is Megan.** She reasons, she decides, she calls tools. She does not manage the environment.
**Arconaut is the ship.** It maintains state, injects context, runs ambient systems, coordinates runtimes.

## 12. Tempo — Turn Structure Governance (Decided)

**Tempo** governs the character of the Soul's turn loop. Set by operator or auto-detected by Arconaut logic.

| Tempo | Description | Tool:Chat Ratio | Use Case |
|-------|-------------|-----------------|----------|
| **`Metronome`** | Default call-and-response | 1:1 | Discussion, exploration, Q&A |
| **`Tuned`** | Adjusted based on present activity | Variable: 1:1 (discussion) → 10:1 (deep implementation) | Implementation, debugging, refactoring |
| **`Evolving`** | Adaptive on multiple axes | Auto-varying | _Deep water — later phase_ |
| **`MainCharacter`** | Almost fully autonomous | 50:1 or higher | Long-running tasks from spec |

### Tempo: Metronone (Default)
```
user → llm → response → wait for user
        ↓
   (may use 0-3 tools, narrates each)
```
Standard conversational agent. Each tool call is narrated. User sees everything.

### Tempo: Tuned
```
user → llm → tool1 → tool2 → tool3 → ... → toolN → llm → brief summary → wait for user
```
Agent executes multiple tool calls with minimal narration. Brief summary at the end. User sees high-level progress, not every step.

**Sub-modes:**
- `Tuned::Discussion` — 1:1 ratio, verbose
- `Tuned::Implementation` — 10:1 ratio, minimal narration
- `Tuned::Debug` — 5:1 ratio, focused on test output
- `Tuned::Review` — agent reads code silently, then delivers critique

### Tempo: MainCharacter
```
spec → llm → tool loop (with internal checkpoints)
                ↓
         checkpoint → brief status → continue
                ↓
         (occasionally asks operator clarifying questions)
```
Agent takes a spec and executes autonomously. Internal checkpoints for self-correction. Brief status updates to operator. May interview operator or another model if stuck.

### Tempo Controls

**Operator sets explicitly:**
```
/tempo metronome
/tempo tuned implementation
/tempo maincharacter
```

**Arconaut auto-detects:**
- User asks question → suggest Metronome
- User asks for feature → suggest Tuned implementation
- User pastes 500-line spec → suggest MainCharacter

**Soul requests change:**
- "This looks like a deep implementation task. Shall I switch to Tuned mode?"

### What Tempo Actually Changes

| Aspect | Metronome | Tuned | MainCharacter |
|--------|-----------|-------|---------------|
| **Narration** | Every tool call | Summary only | Checkpoints only |
| **Tool batching** | Sequential, narrated | Parallel where possible | Parallel, autonomous |
| **User interruptions** | Always welcome | Welcome, but agent may ask to continue | Agent may defer to checkpoint |
| **Context injection** | Full Beat every turn | Beat + working set summary | Minimal state, focused on task |
| **Intervention** | Immediate | After batch | At checkpoints |
| **Audit detail** | Full | Full | Checkpoint-level |

## 13. What SOUL Actually Does (Refocused)

After separation of concerns:

### Soul Responsibilities
1. **Turn execution** — LLM loop: request → response → tool extraction
2. **Tool calling** — Decide which tools to call, in what order, with what arguments
3. **Tempo management** — Operate within current Tempo's constraints
4. **Response generation** — Narrate (or not) based on Tempo
5. **Checkpoint decisions** — In MainCharacter, decide when to pause and reassess
6. **Mode transition requests** — Ask operator/Arconaut to change Tempo

### Arconaut Responsibilities
1. **Context assembly** — Build the prompt: history + Beat + injected context + Vectored results
2. **Ambient intelligence** — Heuristic detection, Vectored auto-fire, Neurotic auto-fire
3. **Runtime management** — Neovim, Brush, BufferManager, Web, Vision lifecycle
4. **Physical plant** — File I/O, process management, network calls
5. **Operator interface** — Slash commands, railroad signals, TUI coordination
6. **Audit & logging** — Record everything, structured shell log, audit partitions
7. **Heuristic engine** — Detect flailing, drift, struggle; feed signals to Soul
